A privacy or compliance reviewer already works from frameworks like the EU AI Act and GDPR. [`get_plan_audit_logs`](/docs/governance/campaign/tasks/get_plan_audit_logs) gives them raw governance entries. This page defines the missing step: a **projection** that joins those entries to a framework's requirements and says, per requirement, what the protocol evidences, what it only partly evidences, and what it does not carry at all.

<Warning>
**Experimental draft, tracked in [#3959](https://github.com/adcontextprotocol/adcp/issues/3959).** The registry entry format, the evidence vocabulary, and the report shape on this page may change, and the linking direction between frameworks and policies is still an open WG question (see [Open question](#open-question-how-frameworks-link-to-policies)). Nothing here changes a task, schema, or capability. Any MUST on this page binds a projection helper that claims to follow it, not governance agents or sellers.

**A status is not a compliance conclusion.** The protocol evidences inputs to a deployer's compliance work, not compliance itself. `satisfied` means every protocol-evidence predicate for the row held; legal classification, conformity assessment, DPIAs, and the workflows behind human oversight and contestation stay with the deployer. See [Annex III & Article 22 obligations](/docs/governance/annex-iii-obligations).
</Warning>

## Shape of the projection

The projection is a **local computation**, not a protocol task. The buyer already holds the audit log and the framework entry is a static file, so nothing needs to ship to a governance agent and a framework revision does not force a redeploy. A reference helper is expected to live in the SDKs; this page defines only the inputs and outputs so independent implementations agree.

"Track 2" below means the plan-field and agent self-declaration work proposed in #3959 (`lawful_basis`, `consent_context`, `data_transfers[]`, agent self-declaration). None of it is schema yet.

| Input | Required | Purpose |
|---|---|---|
| `audit_log` | yes | One [`get_plan_audit_logs`](/docs/governance/campaign/tasks/get_plan_audit_logs) response, requested with `include_entries: true`. The projection runs per `plan_id`. |
| `supplements.plan` | no | The retained plan revision, exactly as supplied on `sync_plans` and hashed by the governance agent. See [Plan revisions](#plan-revisions). |
| `supplements.brand` | no | The `brand.json` fields a framework cites, such as `data_subject_contestation`, resolved from the plan's `brand.domain` at projection time. The report records the source URL and fetch time. |
| `supplements.operator` | no | Facts the exporting operator asserts, such as a retention statement. Never protocol evidence. |
| framework entry | yes | A file from [`static/registry/frameworks/`](https://github.com/adcontextprotocol/adcp/tree/main/static/registry/frameworks). |

Some evidence lives outside the audit response by design. `human_review_required` is a plan field, so it arrives through `supplements.plan`. `plan_hash` is per entry, not per plan. `escalations[]` and `drift_metrics` sit under `summary`. A projector that reads only the audit response can reach `partial` on human oversight at best.

### Status vocabulary

| Status | Meaning |
|---|---|
| `satisfied` | Every protocol-evidence predicate for the row holds. |
| `partial` | Some evidence is present, or the row's ceiling is partial because the protocol cannot carry the rest. |
| `gap` | The row could be evidenced from the protocol but is not in this input. Either the field does not exist yet, or the input lacks a supplement the row needs. The row's `gap_closure` names the addition that would close it. |
| `not_applicable` | The framework's `applies_when` predicate is false for this plan. |
| `out_of_protocol_scope` | The evidence is not something an advertising protocol should carry (for example bias-testing artifacts). No predicate is evaluated. |

### Evaluating a row

1. If the framework's `applies_when` is false, the row is `not_applicable`.
2. If the row's `protocol_scope` is `out`, the row is `out_of_protocol_scope`.
3. Collect each evidence source, then evaluate the classifier: all `satisfied_when` predicates hold → `satisfied`; otherwise all `partial_when` predicates hold → `partial`; otherwise `gap`.
4. A row with `protocol_scope: "partial"` omits `satisfied_when`, so it can never exceed `partial`. A row that depends on `operator_attestation` evidence appears only in `partial_when` for the same reason.

### Plan revisions

Plan-field evidence is only as good as the revision it came from. `plan_hash` is [recomputed over the plan as supplied on `sync_plans`](/docs/governance/campaign/specification#plan-binding-and-audit) (RFC 8785 JCS, SHA-256, minus the [closed list of bookkeeping fields](/docs/governance/campaign/specification#excluded-fields)). A projector MUST compare the recomputed digest to each entry's `plan_hash` by base64url-decoding both to 32 raw bytes, as the specification requires, and MUST use plan-field evidence only against entries whose `plan_hash` matches the supplied revision. When entries carry more than one `plan_hash`, the plan was re-synced mid-flight: supply one revision per hash and project each set of entries against its own revision, otherwise plan-field evidence is treated as absent.

The governance agent sets or overrides `human_review_required` from resolved policies. If the buyer's retained copy lacks the value the agent hashed, the hashes will not match and the row falls back to `partial`; use the revision the agent attested to.

## Registry entry format (prototype)

Each framework is one JSON file under `static/registry/frameworks/`, marked `"x-status": "experimental"`. Frameworks reference policies; policies do not reference frameworks. The excerpt below is a registry-file fragment, not a protocol payload, so it has no `$schema` and is marked `test=false`.

```json test=false
{
  "requirement_id": "art_14_human_oversight",
  "framework_section": "Art. 14",
  "protocol_scope": "in",
  "evidence_sources": [
    { "evidence_id": "plan_human_review", "kind": "plan_field", "selector": "$.human_review_required" },
    { "evidence_id": "check_entries", "kind": "audit_field", "selector": "$.entries[?@.type == 'check']" },
    { "evidence_id": "human_reviewed_count", "kind": "audit_field", "selector": "$.summary.statuses.human_reviewed" },
    { "evidence_id": "escalations", "kind": "audit_field", "selector": "$.summary.escalations[*]" }
  ],
  "classifier": {
    "satisfied_when": [
      { "evidence": "plan_human_review", "op": "eq", "value": true },
      { "evidence": "check_entries", "op": "all_have_fields", "value": ["reviewed_by", "reviewed_at"] },
      { "evidence": "check_entries", "op": "all_field_eq", "field": "mode", "value": "enforce" },
      { "evidence": "escalations", "op": "all_have_fields", "value": ["resolution", "resolved_at"] }
    ],
    "partial_when": [{ "evidence": "human_reviewed_count", "op": "gt", "value": 0 }]
  },
  "gap_closure": "..."
}
```

| Element | Notes |
|---|---|
| `kind` | `audit_field` (selector against the plan's audit object), `policy_evaluated` (a `policy_id` found in any `entries[].policies_evaluated`), `plan_field`, `brand_field`, or `operator_attestation` (selectors against the matching supplement). `policy_evaluated` ignores verdict and mode; a classifier that cares tests them on the entries. |
| `selector` | [RFC 9535](https://www.rfc-editor.org/rfc/rfc9535) JSONPath. `audit_field` selectors are rooted at the one `plans[]` member being projected. |
| `field_status: "proposed"` | The selector targets a field not in any released schema. It resolves to nothing, so the row cannot pass until the field exists. |
| `shared_evidence` | Evidence sources any requirement in the file may reference by `evidence_id`. |
| `applies_when` | Optional file-level predicates. When false, every row is `not_applicable`. `applies_when_note` states how reliable the test is; `jurisdictions` is informational and is not evaluated. |
| `gap_closure` | One line on what addition would close or raise the row. It feeds the report `narrative` for `gap` and `partial` rows. |

Predicates have no expression language. Each names an evidence source and one operator, and runs over the nodes the selector matched. Every operator is false when the selector matched no nodes.

| `op` | True when |
|---|---|
| `present` | At least one node matched. |
| `non_empty` | At least one node matched, and a lone matched array, object, or string is not empty. |
| `eq`, `gt`, `gte` | The first matched node compares true against `value` (a literal) or against the first node of the source named by `value_ref`. |
| `all_have_fields` | At least one node matched, and every node has every field named in `value`, non-null. |
| `all_field_eq` | At least one node matched, and every node's `field` equals `value`. |

`policy_evaluated` sources name registry policies such as `eu_ai_act_annex_iii` and `eu_gdpr_special_category_targeting`. There is no CI cross-validation in this draft.

## EU AI Act (Regulation (EU) 2024/1689)

Obligations for Annex III high-risk ad-targeting decisions. Arts. 10, 12, and 14 are provider design obligations: a deployer's governance stack can surface evidence for them but does not discharge them. Art. 26 is deployer-side. Rows are `not_applicable` unless the `eu_ai_act_annex_iii` registry policy was evaluated on the plan; that match is a heuristic and can over-include (the policy also covers `pharmaceutical_advertising`, which is not an Annex III category). Entry: [`eu_ai_act.json`](https://github.com/adcontextprotocol/adcp/blob/main/static/registry/frameworks/eu_ai_act.json).

| Requirement | Evidence | Status (best case today) | What closes the gap |
|---|---|---|---|
| Art. 10 data governance | `entries[].policies_evaluated` includes `eu_gdpr_special_category_targeting` | `partial` | Restricted-attribute screening is evidenced; dataset provenance and quality need agent self-declaration (Track 2). |
| Art. 10(2)(f)-(g) bias examination | none | `out_of_protocol_scope` | Provider-side model lifecycle artifacts. A declarative pointer could ride on agent self-declaration. |
| Art. 12 record-keeping | check `entries[]` with `timestamp`, `caller`, `verdict`, `plan_hash` | `satisfied` | Evidences the governance decision log, not the underlying system's logs. Needs `include_entries: true`. |
| Art. 14 human oversight | plan `human_review_required`; every check entry has `reviewed_by`, `reviewed_at`, and `mode: enforce`; `summary.escalations[]` resolved | `satisfied` with the matched plan revision; `partial` otherwise, including when any check was unreviewed or ran in `audit` mode | Reviewer competence and the review workflow are outside the protocol. |
| Art. 14(4)(b) automation bias | `summary.drift_metrics.escalation_rate` against `thresholds.escalation_rate_min` | `partial` | The rate is a proxy and the threshold is operator-configured. Awareness of automation bias needs an attestation outside the protocol. |
| Art. 26(6) log retention | operator retention statement | `partial` | `get_plan_audit_logs` carries no retention period or chain-of-custody guarantee. |

## GDPR (Regulation (EU) 2016/679)

Controller-side evidence for ad targeting. No row reaches `satisfied` today: the protocol evidences inputs, and the rest is deployer workflow or a field that does not exist yet. GDPR scope turns on establishment, target audience, and processing location, which `plan.countries` does not reliably capture, so every row is evaluated and the deployer decides which apply. Entry: [`gdpr.json`](https://github.com/adcontextprotocol/adcp/blob/main/static/registry/frameworks/gdpr.json).

| Requirement | Evidence | Status (best case today) | What closes the gap |
|---|---|---|---|
| Art. 6 lawful basis | plan `lawful_basis` (proposed) | `gap`; `partial` once declared | Add a `lawful_basis` enum to `sync_plans` (Track 2). A declaration states the basis relied on, not that it is valid. |
| Art. 9 special categories | `policies_evaluated` includes `eu_gdpr_special_category_targeting` | `partial` | The Art. 9(2) condition needs a `consent_context` block (Track 2). |
| Art. 12 modalities | `brand.data_subject_contestation` | `partial` | Request intake and the one-month clock are deployer workflow. |
| Art. 13 information at collection | `brand.privacy_policy_url` | `partial` | A URL is weak evidence of a notice. `lawful_basis` and `data_transfers[]` (Track 2) would let its statements be checked. |
| Art. 14 information not from the subject | `brand.privacy_policy_url` | `partial` | As Art. 13, plus a per-check signal-source record for the Art. 14(2)(f) source of data. |
| Art. 22 automated decisions | `summary.statuses.human_reviewed`; `brand.data_subject_contestation` | `partial` | Human review of campaign checks is not meaningful involvement in decisions about data subjects. Art. 22(3) contestation is a deployer workflow; "solely automated" is a legal call. |
| Art. 30 records of processing | check `entries[]` with `timestamp`, `caller`, `policies_evaluated` | `partial` | The audit log is an input to the record, not the record. Purposes, transfers, and retention are absent. |
| Ch. V international transfers (Arts. 44-50) | plan `data_transfers` (proposed) | `gap` | Add `data_transfers[]` (Track 2). A plan declaration states intent only; proof needs location evidence from each provider. |

Residency evidence deserves care. Where a governance vendor stores its own control-plane data is deployment compliance and stays out of protocol. Where a seller, signal, or measurement provider processes or stores governed campaign data is a cross-party fact a buyer agent may need before committing spend, and a plan declaration cannot prove it.

### Projected output: EU AI Act

`plan_hashes` is an array because entries carry `plan_hash` per plan revision, so a plan re-synced mid-flight yields more than one. `plan_hash_matches_retained_revision` records only that the retained revision hashes to the entries' value; it does not verify the signed `governance_context` tokens. `evidence[].refs` are RFC 6901 JSON Pointers into the input. Art. 10(2) is the `out_of_protocol_scope` row, and this report holds no `gap` rows because every in-scope requirement has at least partial evidence. ## Open question: how frameworks link to policies

[#3959](https://github.com/adcontextprotocol/adcp/issues/3959) asks whether the link between frameworks and policies is:

- **Option A, bidirectional.** `PolicyEntry` grows an optional `framework_references[]`, and CI checks both directions.
- **Option B, unidirectional.** Frameworks name policies in `evidence_sources`; `PolicyEntry` is unchanged.

This draft uses the Option B shape because it needs no schema change and leaves every existing policy file untouched. It is not a decision. The recommendation is in the WG decision brief on the issue.

## Not covered

- **SDK helper.** Reference projection code is out of this repository.
- **Track 2 fields.** `lawful_basis`, `consent_context`, and `data_transfers[]` are proposals, not schema.
- **Other frameworks.** AIGP, NIST AI RMF, ISO/IEC 42001, Colorado AI Act, MRC, TAG, and DBCFM mappings wait on the linking decision.
- **Export envelope.** A regulator-facing export would also want an export-level digest or signature, retention statement, issuer identity, and per-action `governance_context` verification. That is a follow-on to the projection shape here, and standardizing the bundle becomes protocol work only if heterogeneous parties need to exchange and verify it.
