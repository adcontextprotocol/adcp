[搭建代理](/zh/dist/docs/3.2.3/building/by-layer/L4/build-an-agent)那条 2–8 分钟的路径，给你的是一个符合协议的代理。本页讲的是那之后的事：每一次工具调用背后的业务设施，以及由谁来运行它。

这里的完整例子是**销售代理**，因为它需要的设施最多。信号、创意和零售媒体代理在运营关注点上的差别，用短的提示标出。

## SDK 已经处理的部分

在列出还缺什么之前，先说清楚：一个通过故事板验证的代理已经给你这些：

- AdCP 工具模式和带类型的注册
- 能通过合规检查的请求与响应形状
- 错误格式和版本协商
- 一组示例产品，你可以换成真实产品

下面每一项，都是这些工具处理函数背后的东西。

## 合作、自托管，还是自建

上线代理有三条路径。差别在于你拥有多少，不在于你是不是什么都不拥有——无论哪条路径，产品、定价，以及接入你自己的广告服务器，都仍然归你。

**与托管销售代理平台合作。** 平台运行代理端点、保存状态，并给广告运营团队提供管理产品、定价和审批的后台。你接入自己的广告服务器；平台处理协议，以及协议周围的运营。上线最快，控制最少。

**自托管现成代理。** 把已有的开源代理部署到你自己的基础设施上，再接到你的系统。今天这通常是 [Prebid Sales Agent](https://github.com/prebid/salesagent)，一个带 GAM 集成的社区全栈卖方代理。你不用写协议层和后台界面，但要自己负责托管、升级、数据库，以及广告服务器接线。这是中间地带：比合作控制更多，比自建工作更少。

**自己搭建。** 用 SDK 和技能文件写一个定制代理。你对业务逻辑、定价模型和接入路径有完整控制，代价是代码和其余一切都要自己拥有。当没有现成代理适合你的技术栈或定价模型时，这是对的答案。

三条路径上，SDK 和故事板覆盖的都是协议符合。下表里的每一项都在这条线之外，与你走哪条路径无关。

## 你仍然需要搭建或准备的东西

| 组件 | 它做什么 | 做法举例 |
|---|---|---|
| **产品与定价管理** | 让广告运营在不改代码的情况下定义产品、刊例、打包和可售情况。技能文件里的示例产品是写死的；真实代理需要它们可以动态修改。 | 合作平台的产品目录、现成代理的后台（例如 Prebid Sales Agent），或由数据库支撑的定制后台。 |
| **持久存储** | 跨请求保存产品、定价、媒体购买、创意分配和投放状态。 | PostgreSQL、MySQL，或团队熟悉的任何数据存储。 |
| **创意审核与政策** | 在创意上线前做品牌安全、法律和格式检查。协议只运送创意；接不接受，由你的政策决定。 | 人工审核队列、自动政策引擎（IAB 类别、品牌名单），或两者混合。广告运营团队最容易低估的，往往是这一项。 |
| **投放接入与履约** | 把一笔已售出的媒体购买变成广告服务器里的在投活动。这部分完全在 AdCP 之外，通常也是最难的一块。 | *人工：* 用邮件或 Slack 提醒广告运营在 GAM 里建活动。*半自动：* 用 Google Ad Manager API 创建订单项并分配创意。*全自动：* 从购买确认到实际投放的端到端管道。 |
| **投放报告与效果** | 用真实数字支撑 `get_media_buy_delivery` 和 `provide_performance_feedback`。协议工具已经在；背后的日志接入、聚合和归因管道要你来建。 | 从广告服务器报告 API 拉取、把日志级数据送进数仓，或用托管分析工具喂给代理。 |
| **订单管理** | 跟踪购买状态、审批流程、创意截止时间和投放节奏，这些超出协议任务生命周期所覆盖的范围。 | 起步时用数据库里的状态字段；量上来之后再做仪表板。 |
| **托管** | 让代理一直可在你于运营方 `brand.json` 和媒体方 `adagents.json` 里声明的 URL 上访问。宕机或 URL 漂移会让买方核验失败。 | 云虚拟机、容器服务（Cloud Run、ECS、Fly.io），或托管平台。 |
| **发现与授权记录** | 告诉买方代理：谁运营这个端点、签名密钥在哪里、哪家媒体方授权它卖哪份库存。协议支持由 `get_adcp_capabilities` 声明。 | 发布运营方 `brand.json` 和媒体方 `adagents.json`。见[卖方设置](/docs/brand-protocol/seller-setup)（英文）和[已授权媒体资产](/docs/governance/property/authorized-properties)（英文）。 |

## 协议在哪里结束，你的业务从哪里开始

AdCP 定义的是代理之间对话的形状。它不定义：

- **定价策略** — 你如何给库存定价、刊例如何浮动、折扣何时生效
- **审批政策** — 你接受或拒绝哪些活动，依据是什么
- **账单与开票** — 规范层没有账单；你和买方在带外对账
- **身份与同意** — 用户级身份、同意采集和数据主体权利受监管，而且因实现而异
- **SLA 监视** — 代理端点的可用性、延迟和错误预算
- **广告运营工作流** — 团队如何监视投放节奏、补量和升级

合作平台会替你给其中大部分做默认选择；自托管的现成代理给你一套可以改的默认值；自建代理则要求你自己做每一个决定。

## 不同代理类型的差别

上面的组件表假设的是销售代理。其他类型大部分相同，但各有增补：

- **信号代理** — 同意和来源是承重的。你需要说得清的数据谱系（一个细分从哪来、什么同意覆盖它），以及兑现退出的能力。接入更少是广告服务器排期，更多是把细分送到已经能接收它们的平台。
- **创意代理** — 资产存储、转码和渲染 SLA 取代广告服务器排期。创意审核变成「你愿意渲染什么」的政策，而不是「你愿意投放什么」。
- **零售媒体代理** — 目录新鲜度是运营约束；SKU 一变，产品就变。接入常常走零售专用广告平台，而不是 GAM。

## 在生产环境里运营代理

符合协议的代理，不等于运营良好的代理。这是两件事：**持续的广告运营健康**（协议里的东西确实在干活），以及**安全**（这些东西在干活时仍然可信）。两者都要和你对待广告服务器集成一样认真。

### 广告运营健康监视 — 你实际要看什么

这是日常工作。其中大部分是任何广告运营团队已经在做的监视，再加上对协议的了解。要点不是「要学一套新概念」，而是「仪表板里需要这些具体的协议信号」。Addie 可以帮助你把它们搭起来。

| 要看什么 | 为什么重要 | 该告警的信号 |
|---|---|---|
| **未完成任务队列深度** | 异步任务（`create_media_buy` 提案、`sync_creatives` 审批、`si_initiate_session`）会在审批人落后时堆积。队列深，意味着买方在等。 | 任务打开时间超过 SLA（例如创意审批超过 4 小时）、最老任务的年龄在上升、队列增长快于排空。 |
| **创意审批吞吐** | 创意必须真的被批准或拒绝。一条悄悄停住的队列，看起来和「一切正常」一样——只是购买没有启动。 | 批准/拒绝率相对提交率、超过预期审核窗口仍为 `pending` 的创意、拒绝原因分布。 |
| **生命周期转换是否按时发生** | 卖方必须在投放日期到达时把 `pending_start` 转到 `active`。错过转换会让活动从未投放，尽管它们「创建」得很好。 | 投放开始后仍停在 `pending_start` 的购买、创意到达后仍停在 `pending_creatives` 的购买、本应自动恢复却仍为 `paused` 的购买。 |
| **Webhook 交付健康** | Webhook 是买方得知异步状态变化的方式。静默的交付失败会让买方改为轮询——或者不轮询，从而完全错过事件。 | 失败交付率、重试积压、死信队列大小、从状态变化到成功推送的时间。 |
| **无法上线的购买，其状态是否正确** | 不能上线的活动（创意被拒、账户暂停、政策拒绝）必须反映在状态里，不能静默卡住。治理依赖这一点。 | 既不在投放、也不呈现终态或受阻状态的购买；广告服务器状态与 AdCP 状态不一致。 |
| **投放报告的新鲜度与准确性** | `get_media_buy_delivery` 应当返回当前数字。陈旧报告意味着买方在对着谎言优化。 | 最后更新时间落后、花费增量与广告服务器日志对不上。 |
| **幂等缓存行为** | 重试的 `create_media_buy` 必须返回缓存响应，而不是再创建一笔。合规在沙箱里测这一点；生产漂移本身就是信号。 | `IDEMPOTENCY_CONFLICT` 比率（买方缺陷，或攻击者在探测）、进行中工作出现 `IDEMPOTENCY_EXPIRED`（TTL 太短）、广告服务器里出现重复媒体购买（缓存失败）。 |
| **错误码分布** | 某个买方的某个错误码突然升高，通常是真实问题的第一个信号。 | 每个买方每小时的前 N 个错误码、以前没见过的新错误码。 |

无论代码是谁写的，销售代理都需要这套监视。合作平台应当为其中大部分提供仪表板；自托管的现成代理要求你自己接上；自建代理则把每一行都放在你的团队身上。

### 安全监视 — 合规覆盖什么，什么仍归你

**AdCP 的大部分安全机制由[合规套件](/docs/building/verification/validate-your-agent)强制（英文）——你不需要手工逐项核验。** 故事板运行器对照你的代理核验认证、幂等、模式符合、错误处理和治理行为。套件通过，线路层行为就是对的。你不需要去学代理/账户范围的内部细节、JWS 核验步骤或规范 JSON——测试会做。

合规套件检查这些（所以你不必再教一遍）：

| 故事板 | 它核验什么 |
|---|---|
| `security_baseline`（通用） | 受保护操作要求认证；无效密钥被拒绝；API 密钥或 OAuth 2.0 至少有一种被正确宣告。 |
| `idempotency`（通用） | 会改变状态的请求遵守 `idempotency_key`：重放返回缓存，冲突返回 `IDEMPOTENCY_CONFLICT`，缺键返回 `INVALID_REQUEST`。 |
| `schema-validation`、`error-compliance` | 响应符合模式；错误使用标准分类。 |
| 协议与专业方向故事板 | 各协议行为（媒体购买生命周期、创意工作流、信号激活）端到端正确。 |
| 请求签名测试向量 | RFC 9421 签名请求在 25 个以上的正例和反例上都能正确校验。 |

**无论代码是谁写的，这些仍然归你：**

| 关注点 | 你决定并运行什么 |
|---|---|
| **凭据存储与轮换** | 把令牌放在 KMS 或密钥管理器里。写权限令牌用短寿命（≤24 小时；能承诺花费的令牌考虑 ≤1 小时）。绝不完整记入日志，绝不提交进仓库。合适的轮换节奏取决于泄漏令牌的爆炸半径——为自己的选择写出理由，不要照抄一个数字。 |
| **密钥仪式与破玻璃** | 为高价值密钥（webhook 密钥、治理签名密钥）的生成、转运和销毁写下流程。为事件恢复保留密封的破玻璃凭据，以及使用它们时留下审计轨迹的步骤。 |
| **幂等重放 TTL** | 声明 `capabilities.idempotency.replay_ttl_seconds`——下限 1 小时，建议 24 小时，上限 7 天——并核验声明值与实际缓存保留一致。现成代理把这做成配置；自建则写进实现。 |
| **跨实例与多区域故障转移** | 幂等缓存、会话存储和 webhook 去重状态必须在实例重启后仍然存在，并在水平扩展的实例之间共享。多区域部署里，缓存必须足够一致，使路由到区域 B 的重试能重放最初在区域 A 处理的购买。仅内存的状态会在第一次 Pod 重启时打破至多一次保证。 |
| **安全信号监视** | 留意 `IDEMPOTENCY_CONFLICT` 尖峰（探测）、治理核验失败（冒充）、来自同一对手方的 SSRF 拒绝、来自同一对等方的 401/403 尖峰。和运营监视同一块仪表板，只是告警不同。 |
| **对手方的供应商风险** | 你的治理代理、信号提供方、创意供应商都持有凭据，或签发会影响你活动的签名令牌。像评估任何处理方一样评估他们：披露政策、泄露通知承诺、合规证明、可用性 SLA。 |
| **事件响应手册** | 知道如何在一小时内吊销被攻破的凭据、轮换 webhook 密钥、通知对手方，并在你签发治理令牌时发布一条 `revoked_kids`。在真的需要之前先做桌面演练。 |

如果你在**合作**，问供应商：「你们是否在每次发布时都通过 AdCP 合规套件？哪个版本？我能看最近一次运行吗？」这一个问题覆盖了大部分代码控制面。再问他们是否持有 SOC 2 Type II、ISO 27001，或你所在行业的同等证明，以及泄露通知承诺是什么。如果你在**自托管现成代理**，对着你自己的部署跑合规套件。如果你在**自建**，合规套件就是你的回归套具。

<Note>
**给安全和 IT 负责人：** [安全模型](/zh/dist/docs/3.2.3/building/concepts/security-model)是写给你们的——品牌、代理商、媒体方和平台上的 CISO、安全架构师和第三方风险复核人。它解释威胁面，以及 AdCP 在设计上防御什么，并附有上线前要问工程团队（或供应商）的问题清单。
