本指南面向**已经在生产环境运行 AdCP 代理**、又想迁到官方 SDK、但不能做一次切换日重写的采用者。你的代理在服务真实流量；现有技术栈是工程师自己建的，他们会维护它；你承受不起长达数周的冻结。路径是增量的：一次换一层，每一步之后都发布，并在过程中重新认证。

如果你是从零开始，这份文档不适合你——见[搭建代理](/zh/dist/docs/3.2.3/building/by-layer/L4/build-an-agent)。如果你还在决定要不要迁移，见构建总览上的[手写实现再评估检查](/zh/dist/docs/3.2.3/building#two-checks-before-you-start)。

## 0. 盘点你今天拥有什么

在替换任何东西之前，按[AdCP 栈](/docs/building/cross-cutting/sdk-stack)（英文）的每一层写下你的手写栈提供了什么。用那篇文档里的 L0–L3 清单做标尺。每一行标成：*已交付* / *部分* / *还没有*。

这决定操作顺序。风险最低的替换，通常是你今天覆盖**最少**的那一层，因为要调和的既有行为最少。

## 1. 改任何代码之前，先达到规范符合

最重要的一步：

1. 在你的代理里立一个**模拟模式账户**。（如果还没有 live / sandbox / mock 的区分，见下面的[账户模式不匹配](#account-mode-mismatch)——先在边界上加上这个标志。）
2. 把模拟模式流量接到参考模拟服务器。
3. 对着你的代理跑 AdCP 故事板（见[一致性](/docs/building/verification/conformance)和[验证你的代理](/docs/building/verification/validate-your-agent)，均为英文）。
4. 读通过/失败报告。

失败清单就是你的迁移待办，而且已经排好序。它把「我觉得 SDK 有价值」变成「这是我们没通过的故事板，以及每一条指向哪个 L3 组件」。没有这一步，你是在按销售话术买 SDK，而不是按测到的差距。

你可能会发现自己比想象中更符合（迁移就比预期小），或更不符合（采用 SDK 的理由就更强）。两种结果都有用。

## 2. 操作顺序（风险从低到高）

建议的替换顺序：

1. **一致性测试表面**（[`comply_test_controller`](/docs/building/by-layer/L3/comply-test-controller)，英文）。纯增量——模拟模式流量现在走 SDK；线上流量不动。当场获得规范符合认证。
2. **错误码目录**。用 SDK 的错误构建器替换你自己的错误封套构造。恢复分类和错误码优先级（例如 `NOT_CANCELLABLE` 优先于 `INVALID_STATE`）一并得到。见[错误处理](/docs/building/by-layer/L3/error-handling)（英文）。
3. **幂等缓存**。风险最高的一次替换——见[两级串联的幂等缓存](#two-idempotency-caches-in-series)。规范契约：[幂等](/docs/building/by-layer/L1/security#idempotency)（英文）。
4. **异步任务存储 + 分发器**。采用 SDK 的 `task_id` 加终态制品契约。常常会碰到你的工作队列。见[任务生命周期](/docs/building/by-layer/L3/task-lifecycle)（英文）。
5. **状态机**，一次一个资源。如果媒体购买是你维护时间花得最多的地方，就先做 MediaBuy（[生命周期参考](/docs/media-buy/media-buys/lifecycle)，英文）。每换一个之后重跑生命周期故事板。
6. **Webhook 发出**（签名、重试、幂等）。与第 1–5 步独立，可以并行。见 [Webhook](/docs/building/by-layer/L3/webhooks)（英文）。
7. **RFC 9421 签名与核验**。与上面全部独立，可以并行。见[安全实现](/docs/building/by-layer/L1/security)（英文）。
8. **认证 / 账户存储**。放在最后。你手写的 L2 多半编码了不容易搬走的业务决定。

你可以在任何一步停下来。采用到 L3（第 1–6 步）而不采用 L2，是完全正当的终点——你的认证层继续做它在做的事，SDK 接管协议语义。见[可以继续手写的部分](#5-what-you-can-leave-hand-rolled)。

## 3. 要留意的冲突模式

这些是「两套栈互相打架」的失败模式。看不见它们，增量迁移就会很痛。

<a id="two-idempotency-caches-in-series"></a>

### 两级串联的幂等缓存

你现有的缓存在边界上拦截请求；SDK 的缓存在协议边界上拦截请求。症状：同一个 `idempotency_key`，先命中哪一层缓存，返回的封套就不同；跨载荷复用被一层发现、另一层没有。

**处理。** 选一个，停掉另一个。通常停掉你自己的——SDK 的缓存在 `IDEMPOTENCY_CONFLICT` 上强制*不回显载荷*不变量（被盗密钥的读取预言机威胁），并做规范所要求的跨载荷冲突检测。如果你必须保留自己的存储后端（Redis、Postgres），把 SDK 的缓存契约指到它上面，做成自定义后端，而不是分叉 SDK。

<a id="account-mode-mismatch"></a>

### 账户模式不匹配

SDK 区分 `live` / `sandbox` / `mock` 账户（见[沙箱](/docs/media-buy/advanced-topics/sandbox)，英文）。如果你的手写栈没有这个区分，模拟模式故事板可能会分发到线上处理函数。症状：故事板改动了生产状态；一致性认证拒绝分发。

**处理。** 在采用 SDK 的一致性控制器之前，先在边界上加上账户模式标志。`comply_test_controller` 拒绝在任何不是 sandbox 或 mock 的账户上运行——这个拒绝是特性，不是缺陷。

### Webhook 签名归属

如果两套栈都试图给出站 webhook 签名，接收方会看到两个 `Signature` 头（或者一个赢了，另一个被代理静默覆盖）。无论哪种，签名都核验不过。

**处理。** 在边界上只留一个签名方；通常是 SDK 的，因为它对照公钥注册表跟踪密钥轮换，并正确处理 RFC 9421 规范化。保留你由 KMS 支撑的密钥材料；把 SDK 的签名提供方抽象配置成使用它。

### 状态机漂移

你手写的状态机多半有 SDK 会拒绝的边（例如从 `pending_creatives` 直接到 `completed`，跳过 `active`；或者 `active` 到 `canceled`，却不区分 `NOT_CANCELLABLE` 与 `INVALID_STATE` 的优先级）。症状：生命周期故事板在你预期成功的地方以 `INVALID_STATE` 失败。

**处理。** 在换状态机*之前*，先对着你的代理跑生命周期故事板。把你的边集合对齐到规范——修明显的缺陷，对含糊之处提交规范问题。然后再换上 SDK 的状态机；它会强制执行你刚刚手工收敛到的那套规则。

### Webhook 交付传输

如果你的队列或工作器今天已经在交付 webhook，在没有停掉自己的发出器之前接上 SDK 的发出器，会造成双重交付。症状：接收方在略有差别的时间看到相同载荷、重复的幂等键。

**处理。** SDK 构建封套；怎么送出去是你的事。把 SDK 配置成交给现有传输，而不是跑它内置的 HTTP 交付——接缝就在这里。

### 模式校验碰撞

如果你用自己的模式包校验入站载荷，SDK 又在自己的边界上再校验一次，结果要么是重复劳动（便宜），要么是结论矛盾（真缺陷——你的包相对已发布模式漂移了）。

**处理。** SDK 接入之后，停掉你本地的校验器。两者同时运行时，把任何差异都当成你的包过期，而不是 SDK 错了。

## 4. 能通过一致性的中间状态

每一步之后，你都可以重跑模拟模式故事板并重新认证。你不需要做完迁移才能声称符合——你只需要在 SDK 一致性套件所强制的那条切线上通过故事板。

| 步骤之后 | 你拥有什么 | 一致性状态 |
|---|---|---|
| 1 | 接上一致性控制器；代理本身未改 | **规范符合**（模拟模式故事板对着你未改动的 L3 运行） |
| 2 | 加上 SDK 错误封套 | 相同；恢复语义更好 |
| 3 | 加上 SDK 幂等 | 相同；跨载荷复用上的安全更紧 |
| 4 | 加上 SDK 异步任务契约 | 相同；任务生命周期统一 |
| 5 | 加上 SDK 状态机 | 相同；转换校验不再是你的问题 |
| 6 | 加上 SDK webhook 封套 | 相同；已签名、会重试、带去重键 |
| 7 | 加上 SDK 签名 | **线上符合**（当那组故事板发布之后） |
| 8 | 加上 SDK 账户存储 | 完整的、建在 SDK 上的 L4 |

每一步之后都发布。生产流量保持在线。

### 每一步的回滚

替换顺序里的每一步都应当能在大约 5 分钟内逆转。总模式是：每次替换都是**用手写组件和 SDK 组件之间的功能标志切换**，而不是删除。你把替换放在按账户的标志后面发布，观察，然后翻转默认值。回滚就是把同一面标志翻回去。

按替换来计划：

| 步骤 | 回退机制 | 可能泄漏了什么状态 | 回滚后首先核验什么 |
|---|---|---|---|
| 1. 一致性控制器 | 在模拟模式账户上禁用 SDK 路由 | 无——模拟模式按设计只走沙箱 | 模拟故事板仍然能对着你手写的 L3 通过 |
| 2. 错误封套 | 翻回你的错误构建器 | 切换窗口里的出站封套可能带着 SDK 形状的错误码；依赖旧错误码的下游可能已经记下来了 | 你的错误监视仪表板又在读正确的封套形状 |
| 3. 幂等缓存 | 翻回你的缓存 | **切换窗口里两边缓存都见过流量。** 同一个 `idempotency_key` 现在可能以不同封套同时存在于两个存储。回滚之后，你的缓存是权威的；回退时清空 SDK 的缓存 | 没有因双缓存窗口引起的 `IDEMPOTENCY_CONFLICT` 风暴 |
| 4. 异步任务契约 | 翻回你的任务存储 | 在 SDK 契约下开始的未完成任务，终态制品形状可能和你的工作器预期不同 | 在回退落地之前，排空或中止切换窗口里创建的任务 |
| 5. 状态机 | 翻回你的状态机 | SDK 可能拒绝了你的状态机会接受的转换（或相反）。受影响的资源处在你的代码可能不知道如何推进的状态 | 跑一次对账查询：「有没有任何资源处在两套状态机都合法的状态？有没有任何只在其中一套下合法？」 |
| 6. Webhook 封套 | 翻回你的发出器 | 接收方在切换窗口里收到了 SDK 形状的 webhook。他们可能已经确认。回滚时不要重发 | 你的去重表同时接受新旧 `idempotency_key` 形状（过渡期） |
| 7. RFC 9421 签名 | 翻回你的签名方 | 接收方在窗口里收到了 SDK 签名的 webhook 或响应。他们的密钥注册表必须仍能解析你的旧 `keyid` | 你的旧 `keyid` 仍发布在 JWKS 里 |
| 8. 账户存储 | 翻回你的存储 | 在 SDK 存储下做出的账户解析，可能把流量路由到了和你的存储不同的租户 | 在完全回退之前，对切换窗口里被解析过的账户跑一次对账 |

### 凌晨两点的生产故障

如果第 N 步在凌晨两点的生产环境失败，值班步骤是：

1. **把按账户的标志翻回去**，让受影响账户（如果无法隔离爆炸半径，就全局）回到手写组件。这是止血所需要的唯一步骤。
2. **对照上面该步骤的泄漏行确认。** 大多数步骤都会在某处留下残留状态——记下是什么，这样早上的排查不用从零开始。
3. **不要在事件进行中重跑一致性套件。** 它跑的是模拟模式；生产故障是另一种信号。
4. **把事件记在这次替换步骤上**，而不是记在 SDK 整体上。迁移指南的替换顺序是调查单位；SDK 的覆盖矩阵在它的下游。

**不要计划不可逆的替换。** 如果某一步放不进「标志然后翻转」的模式（例如一次破坏性的模式迁移），把它做成单独的、有名字的项目——不要放进替换顺序。

<a id="5-what-you-can-leave-hand-rolled"></a>

## 5. 可以继续手写的部分

规范有意见的地方，SDK 也有意见；规范没有意见的地方，SDK 是可插拔的。你不必放弃现有基础设施：

- **签名提供方。** 保留你的 KMS 集成。SDK 接受自定义签名方。
- **账户存储。** 保留你的多租户路由。SDK 的账户存储接口就是接缝。
- **幂等后端。** 保留你的 Redis / Postgres。SDK 的缓存契约可插拔。
- **Webhook 交付传输。** 保留你的队列。SDK 构建封套；怎么送出去是你的事。
- **模式校验库。** 如果你想保留自己的校验器也可以；SDK 在自己的边界上用自己的，不用你的。

如果你的手写栈在这些点上已经有好答案，把它们作为**配置**换进去，而不是作为分叉。

## 6. 迁移期间的版本

你会同时对付两条版本轴：

- **买方的规范版本。** 迁移是加上按调用 `adcpVersion` 钉扎的好时机，这样你就不用按买方版本去分叉处理函数。见[版本适配](/docs/building/cross-cutting/version-adaptation)（英文）。
- **SDK 版本。** 不要把迁到遗留导入路径当作最终状态——要*穿过*它。遗留子路径的存在，是为了让你在新入口上一次采用一个专业方向，其余仍留在旧入口。同一项目里的全新代码直接使用新框架。

### 实例：两个买方，替换进行到一半

你在第 3 步（幂等）。买方 A 暂时还在生命周期即将结束的 AdCP 2.5 上，正在迁移；买方 B 在 AdCP 3.0 上。对已经切过去的账户，你已经采用了 SDK 的控制器、错误封套和幂等缓存。买方 A 正在迁往 SDK 的中途；买方 B 在 SDK 上从零开始。这是迁移桥，不是受支持的生产端点终态。

入站一侧：事先识别每个对等方的规范版本（来自代理注册表、代理卡片，或存在时的 `adcp_version` 字段），在代理上或按调用钉扎 `adcpVersion`，让 SDK 适配线路形状。以 `@adcp/sdk` 为例：

```ts
import { ADCPMultiAgentClient } from '@adcp/sdk';

const buyerA = new ADCPMultiAgentClient([{
  id: 'buyer-a',
  agent_uri: 'https://buyer-a.example.com/mcp/',
  protocol: 'mcp',
  auth_token: process.env.BUYER_A_TOKEN,
  adcpVersion: 'v2.5',  // ← per-agent pin, no fork in handlers
}]);

const buyerB = new ADCPMultiAgentClient([{
  id: 'buyer-b',
  agent_uri: 'https://buyer-b.example.com/a2a',
  protocol: 'a2a',
  auth_token: process.env.BUYER_B_TOKEN,
  adcpVersion: '3.0', // ← canonical / current
}]);
```

出站（服务器）一侧，声明*你*接受什么：

```ts
import { createAdcpServer } from '@adcp/sdk/server';

createAdcpServer({
  capabilities: {
    major_versions: [3],
    supported_versions: ['3.0'],
  },
  // …handlers, all on the canonical 3.0 shape;
  // 2.5 callers are translated by client-side adapters before they reach you.
});
```

第 3 步进行到一半时，每个买方的一次调用看起来是这样：

| | 买方 A（2.5 线路） | 买方 B（3.0 线路） |
|---|---|---|
| **入站形状** | 2.5 的 `create_media_buy` | 3.0 的 `create_media_buy` |
| **适配器做的事** | 把 2.5 翻译成 3.0 形状 | 原样通过 |
| **你的处理函数看到** | 3.0 类型对象 | 同样的 3.0 类型对象 |
| **幂等缓存** | SDK 的（你在第 3 步） | SDK 的 |
| **错误封套** | SDK 的，出站时翻译回 2.5 | SDK 的 |
| **出站形状** | 2.5（适配器在出去的路上翻译） | 3.0 |

一套处理函数代码。两种线路版本。两个买方都看到他们预期的封套形状。在第 3 步采用 `adcpVersion` 钉扎成本很低——大部分版本工作在适配器模块里，SDK 已经带上了。

如果你回退（把第 3 步回滚到你手写的缓存），买方 A 仍然经过 SDK 的翻译适配器——版本机制和幂等机制是独立的。回滚时你不用重新分叉处理函数代码。

## 7. 什么时候*不*迁移

如果你的代理为一小群具名买方提供冻结的线路表面，工程师在协议维护上花的时间接近于零，迁移的回报就低。合理的暂缓：

- 你提供冻结的、受支持的 3.x 线路表面，并且有一份写明日期的计划，要在该表面到达生命周期结束之前采用当前发行版。
- 你的一致性差距（来自第 1 步）小到可以就地修，而不采用 SDK。
- 你有硬性的监管或运营理由，必须端到端拥有每一层。

这些情况下，第 1 步仍然要做——把模拟模式接到参考模拟服务器，以获得规范符合认证——然后在 AdCP 4.0，或买方组合发生变化时，再回头看迁移问题。

迁移是给**维护负担真实存在、并且在增长**的采用者的。成本说法（[从零做 L0–L3 大约 3–4 个人月](/docs/building/cross-cutting/sdk-stack#why-sdks-matter-more-in-adcp-than-in-eg-http)，英文）是你通过增量采用*买回来*的东西——但只有在那份维护负担确实存在时才是。
