# What's new in AdCP 3.3

<Warning>
**3.3 is in its beta cycle.** Beta.0 publishes the protocol artifacts before SDK support. Beta.1 incorporates integration feedback, then becomes SDK-backed after a second SDK refresh against the exact beta.1 bundle. Use the beta in development and staging, and read the [3.3 beta program](/docs/reference/3-3-beta) before testing. This page lists only what has merged; the narrative is refreshed at each beta cut.
</Warning>

3.2 added the compact lifecycle and portable evidence. 3.3 is a minor release that so far tightens the places where two conformant 3.2 implementations could still disagree: when an account comes into existence, which agent a signature belongs to, and what a seller's catalog intake accepts.

No stable field, enum value, or task is removed, and 3.3 adds optional fields and declarations. The `seller_id` result fields on event sources and audiences are deprecated in favor of `platform_id`; natural-key account references after provisioning are also deprecated. All remain functional throughout 3.x. Schema-valid 3.2 messages stay schema-valid unless they already used a name 3.3 now defines: `adcp.implementation` (previously an open extension point), `media_buy.features.catalog_ingestion` (previously any boolean was admissible), `dooh_placement_attributes.location` and `dooh_inventory_summary` (previously open extension points; `lon`, not `lng`), and the now-reserved `ext.adcp`. Merged changes narrow what a lazily provisioning seller may do on discovery tasks, which signatures verify, the size of counterparty-asserted domain lists, and how sellers report event source and audience platform IDs. Another change loosens a required field: delivery rows may omit `impressions`, gated on the caller's pin. These are recorded in [Versioning and governance](/docs/reference/versioning#3-3-exceptions-to-3-x-compatibility-beta) and lead the [migration guide](/docs/reference/migration/3-2-to-3-3).

## The 3.3 feature set

### SDK identity and integration depth

Agents can optionally report `adcp.implementation.sdks[]`: package identifiers, exact resolved versions, and the server components they actually use. This distinguishes build-time types or runtime validation from SDK transport, authentication, signing, lifecycle, idempotency, and webhook handling. Missing metadata means unknown SDK use; an empty SDK list explicitly reports none. An SDK entry with `components: []` reports package use without claiming agent-wide coverage. The report helps buyers target checks and investigate known SDK behavior. It is self-reported, does not establish approval or change conformance obligations, and cannot justify certification shortcuts without independently trusted evidence covering the endpoint and integration. See [implementation metadata](/docs/protocol/get_adcp_capabilities#implementation).

### Discovery never provisions an account

Discovery and negotiation tasks, including `get_products`, `list_products`, `get_signals`, `request_proposals`, `refine_proposals`, and `decline_proposals`, MUST NOT create or activate an account, or accept a seller's default terms on a buyer's behalf. A lazily provisioning seller provisions only on a task that commits spend or creates account-owned resources, such as `create_media_buy`, `buy_products`, `accept_proposal`, `sync_accounts`, `sync_creatives`, `sync_catalogs`, `sync_event_sources`, or `activate_signal`. A seller that provisions lazily instead of exposing `sync_accounts` MAY answer a discovery task for a complete natural key it would provision, as if that account existed, without creating it; a seller that exposes `sync_accounts` returns `ACCOUNT_NOT_FOUND`. (An unresolved `account` returning `ACCOUNT_NOT_FOUND`, even where `account` is optional, was already required and was clarified in 3.2.2.)

The advisory storyboard `media_buy_seller/unprovisioned_account_reference` grades this; its checks become required at runner capability `14.1.0`. See [Account references before provisioning](/docs/accounts/overview#account-references-before-provisioning).

### One agent-resolution rule for every signing surface

Request signing, webhook signing, governance JWS `iss`, designated-task response signing, and rights attestations now share one algorithm for deciding which brand.json lists an agent and which keys it may sign with. Agent URLs match by canonical URL everywhere, a publisher's `adagents.json` `signing_keys` pin narrows the accepted keys for sell-side signatures about that publisher's inventory, and webhook discovery starts from `identity.brand_json_url`. TMP keeps its own publisher-key model. See [Agent resolution](/docs/building/by-layer/L1/security#agent-resolution).

This is a verification change: some signatures that verified under 3.2 can fail, mostly webhook and request signing. The list is in the [migration guide](/docs/reference/migration/3-2-to-3-3#signature-verification-tightens).

### Account IDs you can rely on

Sellers SHOULD return `account_id` from `sync_accounts`, and a seller that accepts it on every account-scoped task, for every account, and never changes it declares the optional `account.stable_account_id` capability. Buyers send the ID to those sellers instead of the natural key, so calls after onboarding look the same whichever account model the seller uses. Natural keys keep working throughout 3.x, but using them as the reference after provisioning is now deprecated and planned for removal in 4.0. They remain the way to open an account and to look up its ID. The accounts docs also now describe `require_operator_auth` as who holds the credential, and separate principals (who is calling) from accounts (which advertiser relationship). See [Toward account IDs everywhere](/docs/accounts/overview#toward-account-ids-everywhere).

### Platform object IDs have one name

`sync_event_sources` and `sync_audiences` results now use optional `platform_id` for the object's ID in the seller's ad platform, matching creatives and catalogs. A seller reporting this ID in 3.3 and later 3.x responses MUST emit both `platform_id` and the deprecated `seller_id` alias with identical values, including discovery responses. Buyers MUST prefer `platform_id` and fall back to `seller_id` only when the new field is absent. Continue using `event_source_id` and `audience_id` in AdCP requests. The aliases keep working throughout 3.x; removal is no earlier than 4.0 under the six-month notice policy. Seller identity in `adagents.json` and publisher identifiers is unchanged. See [Deprecations](/docs/reference/migration/3-2-to-3-3#deprecations).

### Catalog ingestion declarations

Sellers can declare what their catalog intake accepts in an optional `media_buy.features.catalog_ingestion` object: accepted catalog types, ingestion modes (`feed_url`, `inline_items`), feed formats, content identifier types, an inline batch limit, and whether item status is reported `per_item` or at the `feed_level`. A seller that declares it must also declare `catalog_management: true`, and must reject an unlisted catalog type, ingestion mode, or feed format, and an explicitly supplied `content_id_type` outside a declared `supported_content_id_types` list, with `UNSUPPORTED_FEATURE` before changing state, including on dry runs. Inline items beyond `max_inline_items_per_request` fail with `INVALID_REQUEST`. A buyer that finds no declaration should treat ingestion limits as unknown, not unlimited. See [`sync_catalogs`](/docs/media-buy/task-reference/sync_catalogs#ingestion-compatibility) and [capabilities](/docs/protocol/get_adcp_capabilities#catalog_ingestion).

### Structured DOOH location

Concrete screens can carry `dooh_placement_attributes.location` (`lat`, `lon`, and a structured `address`) on placements. Network products can carry `dooh_inventory_summary.venue_counts[]` to describe aggregate geography by `geo_level` and `geo_code`. Both are optional disclosure metadata, and `location` never changes placement identity. See [DOOH](/docs/creative/channels/dooh#structured-location-for-planning-and-mapping).

### The `ext.adcp` namespace

`ext.adcp` is now a registered, AdCP-owned extension namespace. Its first member is an optional `opportunity` binding for cooperating 3.2 `get_products` integrations, declared by listing `adcp` in `extensions_supported`. It reuses the published 3.2 `OpportunityContext` shape and is not the core `opportunity` field. The namespace is reserved for the AdCP working group, so vendors keep their own namespaces. See [AdCP opportunity extension](/docs/building/by-layer/L2/context-sessions#adcp-opportunity-extension).

### Open opportunities and later proposals (experimental)

A buyer can keep an opportunity open after the first response and let sellers send more. `opportunity.later_proposals` gives consent with optional `until`, `max_count`, and `min_interval` limits. Sellers then create draft-only later proposals, announce each with the identifiers-only `proposal.created` notification, and serve them through the new [`list_proposals`](/docs/media-buy/task-reference/list_proposals) read, which returns each snapshot beside its disposition. `accept_proposal` and `buy_products` accept an explicit `opportunity.status: "open"` so a buyer can buy part of a plan and keep sourcing. Everything is experimental under `media_buy.open_opportunities` and advertised in parts. See [Open opportunities and later proposals](/docs/media-buy/product-discovery/proposal-negotiation#open-opportunities-and-later-proposals) and [#8096](https://github.com/adcontextprotocol/adcp/issues/8096).

### Bounded agent responses

A seller agent that answers a discovery call with tens of megabytes is an availability attack on every buyer that reads the body before checking its size. 3.3 adds [Response size bounds](/docs/building/by-layer/L1/security#response-size-bounds): clients SHOULD bound every AdCP response they read, enforce the bound while the body is received rather than after buffering or parsing, cover SSE per event and cumulatively, surface an oversized response as an error rather than truncating it, and bound JSON depth and node count once the byte cap passes — the byte cap bounds ingress, the parse bounds bound memory. The default is 4 MiB, matching what the SDKs and the hosted grader ship, and 4 MiB is the ceiling on what any default may be.

This is a recommendation, not a conformance requirement, but the interop effect is real in both directions. A buyer adopting the default rejects a response it would previously have buffered, and the rejection arrives as a mid-body connection abort rather than an `adcp_error`. A buyer still on the older 1 MiB figure rejects a response a 3.3 buyer accepts.

The seller-side counterpart matters more than the number: keep discovery responses small. `tools/list`, `get_adcp_capabilities`, and the A2A agent card are the first bytes a counterparty reads, and an oversized one makes an agent unreachable rather than slow. `get_adcp_capabilities` is the sharpest case — above `MAX_CAPABILITIES_BYTES` your signing keys stop resolving too. See [Discovery responses stay small](/docs/building/concepts/managing-response-size#discovery-responses-stay-small).

### Nobody else gets to write your capabilities document

Two capability fields enumerate relationships a *counterparty* asserts:
`media_buy.portfolio.publisher_domains` and `signals.data_provider_domains` are both
populated from those counterparties' `/.well-known/adagents.json`, which any domain
owner publishes unilaterally and without the named agent's consent. An agent that
mirrored every publisher claiming it had handed an unauthenticated stranger a write
primitive into its own discovery document — and since the signing-key path fetches
that document unnarrowed under `MAX_CAPABILITIES_BYTES`, pushing it past 64 KiB cost
the victim *signature verification*, arriving a cache cycle later with no visible
connection to its cause.

3.3 adds a normative byte budget — one eighth of the capabilities budget for any
single counterparty-asserted field, one quarter for both together — and declares
structural bounds (100 unique entries, 253 characters each) that the conformance
storyboard grades in 3.x and the schema enforces in 4.0. No previously-valid
document becomes schema-invalid; what changes is what counts as conformant. Because a bounded
list would otherwise make a large legitimate network look unauthorized for most of
its own inventory, the bound ships with `publisher_domains_complete` and
`data_provider_domains_complete` — default `true`, set `false` when you truncate.
Both lists are explicitly non-exhaustive, so a buyer must resolve the publisher named
on a product through that publisher's own `adagents.json` and must never read absence
from the list as a denial.

### Clarifications and conformance

- `authorized_agents[].url` in `adagents.json` is the agent's full protocol endpoint URL, including its path, and one entry is needed for each agent URL. See [Agent URL matching](/docs/governance/property/adagents#agent-url-matching).
- Compliance storyboards gate advanced delivery reporting on advertised wholesale discovery support and proposal-finalization replay on advertised idempotency support, exercise the documented polling path in `sales-guaranteed`, and provision an explicit sandbox account in the acceptance-policy discovery scenario. These change grading results, not the wire.
- The trust and verification docs now agree with the schemas: only `verify_brand_claim` and `verify_brand_claims` carry signed response payloads. Examples use `agents[]` instead of the deprecated `brand_agent` and `rights_agent` fields.

The account-reference and trust-docs clarifications already shipped in 3.2.2 ([`v3.2.2`](https://github.com/adcontextprotocol/adcp/releases/tag/v3.2.2)).

## What requires adopter attention

| If you are… | Review before advertising 3.3 |
|---|---|
| A seller that provisions accounts lazily | Stop provisioning on discovery tasks; return `ACCOUNT_NOT_FOUND` for an unresolved `account` unless you answer for the account you would create. |
| A signing or verifying implementation | Resolve agents by canonical URL from `identity.brand_json_url`, and publish every pinned key in the agent's JWKS. |
| A seller that returns account IDs | Return `account_id` from `sync_accounts`; declare `account.stable_account_id` once it is accepted on every account-scoped task and never changes. |
| A buyer that sends natural keys after provisioning | Store the returned `account_id` and send it to sellers that declare `stable_account_id`; natural-key references are deprecated ahead of 4.0. |
| A seller reporting event source or audience platform IDs | Emit `platform_id` and the deprecated `seller_id` alias with identical values, including discovery responses. |
| A buyer consuming event source or audience platform IDs | Prefer `platform_id`, fall back to `seller_id` when absent, and keep using buyer object IDs in AdCP requests. |
| A seller with a catalog intake | Declare `catalog_ingestion` if buyers need your limits, and reject out-of-declaration requests before mutation. |
| A seller that wants to send proposals after the first response | Opt in to `media_buy.open_opportunities`: advertise `list_proposals` first, then `later_proposals` with a `max_open_duration`, and honor buyer consent and limits. |
| A DOOH seller | Add `location` and `venue_counts` where you can disclose them; both are optional. |
| An SDK maintainer | Generate from the signed beta.0 tarball and publish an exact support statement. |
| A buyer or SDK maintainer | Adopt the 4 MiB response-size default; size your aggregate budget, not just the per-call one, if you fan out across agents. |
| Any agent operator | Measure `tools/list`, `get_adcp_capabilities`, and your agent card. Oversized discovery makes you unreachable, and oversized capabilities also breaks signing-key discovery. |
| A compliance operator | Treat beta.0 as an implementation input. Do not issue a 3.3 badge from beta.0. |
