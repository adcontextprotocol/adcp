# What's new in AdCP 3.3

<Info>
**AdCP 3.3 is generally available** (published 2026-12-03). The release artifact is `3.3.0` and the wire pin is `adcp_version: "3.3"`. Send `"3.3"` only after a peer lists it in `get_adcp_capabilities.adcp.supported_versions`. 3.2 stays supported for integrations pinned to `"3.2"`, and nothing forces you to migrate. 3.3 is the last planned 3.x minor: the next feature release is 4.0.
</Info>

3.2 made the deal between agents explicit. **3.3 brings the rest of media into the same buy.** A booking that waits on a traffic log, a host read, or a person's sign-off can say when it will be confirmed. A linear TV, print, or DOOH seller can report what it actually knows, without pretending to be an ad server. And the places where two conformant 3.2 implementations could still disagree are settled.

This page is the adopter overview. The complete record is [Release Notes § Version 3.3.0](/docs/reference/release-notes#version-3-3-0), and the role-based checklist is [Migrating from 3.2 to 3.3](/docs/reference/migration/3-2-to-3-3). If you built against a beta or release candidate, read the [3.3 prerelease history](/docs/reference/3-3-beta) too.

## Why 3.3 matters

1. **Scheduled and human-gated buying.** A buy can carry the time the seller expects to confirm it. Holds can be planned, ranked, and extended. Proposal requests can target an outcome a vendor measures, and a governance plan can budget by period.
2. **Delivery data offline sellers actually have.** Spot lifecycle and makegoods, print proof of insertion and circulation, structured DOOH location and impression basis, property-grain rollups, rows without impressions, and audience sizes as honest ranges.
3. **Schemas open by default.** 3.3 opens the schemas that were closed by accident, so a minor release only adds and an older validator stops rejecting a newer peer for fields it does not know.
4. **Fewer ways to disagree.** An account is its `account_id`. One agent-resolution rule covers every signing surface. Every task response carries the protocol envelope. A response conforms to the release the seller served. Discovery never provisions an account.
5. **Agents that introduce themselves (experimental).** A buyer agent can sign with the Web Bot Auth profile and onboard with a seller it has never spoken to, with no seller-issued credential.

| If you are… | What changes for you |
|---|---|
| **A buyer or agency** | Buy scheduled media, sponsorships, and broadcast in the same flow as programmatic, and know when a booking will be confirmed. Ask for an outcome a vendor measures, budget a governance plan by period, and read honest delivery from offline sellers. |
| **A seller or platform** | Sell what you actually sell: hold inventory under a policy you declare, confirm on your own booking round, report spots, makegoods, tearsheets, and DOOH plays as you record them, and leave out what you didn't measure. Declare fixed-price, non-guaranteed selling with the new stable `sales-fixed-rate` specialism. |
| **An agent or SDK builder** | Open schemas and one protocol envelope on every response make generated types honest. Bounded responses, one agent-resolution rule, and served-release conformance remove the edge cases where two SDKs disagreed. |

3.3 removes no stable field, enum value, or task. Its narrowings of conformant behavior are recorded in one place, [3.3 exceptions to 3.x compatibility](/docs/reference/versioning#3-3-exceptions-to-3-x-compatibility), and lead the [migration guide](/docs/reference/migration/3-2-to-3-3#required-to-claim-3-3-behavior).

## The 3.3 feature set

- **Scheduled and human-gated buying.** `expected_confirmation_at` on submitted buys and finalized proposals, experimental holds (`hold_policy`, ranking, per-installment holds, `extend_hold`), vendor-metric outcome goals, experimental governance budget periods, installment `change_cutoff`, and delegated composition (experimental).
- **Offline and scheduled delivery.** Experimental spot lifecycle and break position, print proof of insertion and circulation, DOOH impression basis, installment lifecycle and proof of publication, and delivery projection; structured DOOH location; property-grain rollups; optional `impressions` on delivery rows; audience size ranges.
- **Proposals.** Experimental open opportunities with later proposals and `list_proposals`, seller offers against an accepted buy, installment refinement, and media-buy lineage; `PROPOSAL_TERMS_CHANGED` for a stale terms digest; signed terms that bind every member.
- **Accounts and principals.** The `account_id` identity model, experimental `request_account` as the single account write, experimental principal-level reporting subscriptions, and a principal defined as the bound buyer agent.
- **Agent identity (experimental).** The Web Bot Auth signing profile, `trust.json`, demand-side grants, seller onboarding posture, and the `adcp-prod-security-3.3` production security profile.
- **Creative.** Declared assignment operations, `replace` that carries the replaced assignment's settings, experimental live creative updates, assignment-scoped landing pages and trackers, hosted video and audio playback events, and carousel card sizes and CTA values.
- **Channels.** Experimental minute-level dayparts, broadcast mezzanine formats and loudness, the NMO and VideoAmp demographic systems, collection cards (experimental), and installments on the compact product lifecycle.
- **Schemas and versioning.** Schemas open by default, the rules for what changes between releases, reserved-word-safe enum values, the protocol envelope on every task response, capabilities bounded by structure, and a major-only request served the oldest supported release.
- **Trust and runtime.** One agent-resolution rule, A2A hardening at MUST, `reporting_webhook.operation_id` that fails closed, bounded responses and inbound bodies, a bundled Public Suffix List, and a 2 MiB brand.json cap.
- **Conformance.** The stable `sales-fixed-rate` specialism, `sales-broadcast-tv` 1.1.0, and storyboards for holds, account requests, reporting subscriptions, declared format options, and assignment operations.

The five new tools are `list_proposals`, `request_account`, `list_collections`, `report_media_buy_issue`, and `get_media_buy_issue`. The new specialism is `sales-fixed-rate`. Nothing was removed from any of the three lists.

## Headline features

### Scheduled and human-gated buying

- **An account is its account ID.** Sellers MUST return `account_id` from `sync_accounts` once the account is resolved, accept it on every account-scoped task, and never change it. A brand is its domain, plus `brand_id` where its `brand.json` lists several brands. Countries, currency, timezone, sandbox, and `operator_unit` are account attributes that a settings update changes without changing the account. Natural keys keep working throughout 3.x as the way to open an account and look up its ID, but using them as the reference after provisioning is deprecated. See [Account identity](/docs/accounts/overview#account-identity).
- **Expected confirmation time.** The `submitted` envelope of `create_media_buy`, `buy_products`, and `accept_proposal` can carry `expected_confirmation_at`. A seller whose confirmation waits on a booking round or a manual review window SHOULD set it, and buyers SHOULD check status at that time instead of polling tightly. `refine_proposals` can carry it on a `submitted` finalize whose hold waits on a person's agreement, such as a creator or host. It is an estimate, not a commitment. See [Expected confirmation time](/docs/media-buy/task-reference/create_media_buy#expected-confirmation-time).
- **Vendor-metric outcome goals.** `criteria.outcome_target.goal` accepts `kind: "vendor_metric"`, so a buyer can plan "5,000 store visits measured by a foot-traffic vendor", optionally with a cost per visit. The seller answers in each forecast point's `vendor_metric_values[]`. See [Vendor-metric goals](/docs/media-buy/task-reference/request_proposals#vendor-metric-goals).
- **Holds you can plan and extend (experimental).** Products and proposals can carry a `hold_policy`, a ranked hold reports its queue position, a committed proposal lists per-installment `holds`, and `refine_proposals` `extend_hold` lengthens a committed hold without re-finalizing. See [Hold policy](/docs/media-buy/task-reference/refine_proposals#hold-policy-experimental).
- **Governance budget periods (experimental).** A campaign governance plan can split its budget by time with `budget.periods[]`, and `check_governance` denies a dated action that straddles a period, sits in unallocated budget, or overruns its period. See [Budget periods](/docs/governance/campaign/tasks/sync_plans#budget-periods).
- **Fixed-price, non-guaranteed sellers.** The stable `sales-fixed-rate` specialism covers sellers in any medium that publish a fixed price, reserve no inventory, make no delivery commitment, and may hold a buy for review. A provisional buy (`confirmed_at: null`) stays `pending_start` until the seller confirms or rejects it. See [Choosing a sales specialism](/docs/building/verification/compliance-catalog#choosing-a-sales-specialism).
- **Change cutoff and failed mutations.** Installment deadlines can carry `change_cutoff`, the last moment a creative swap, pause, or stop still takes effect ([Installment deadlines](/docs/media-buy/product-discovery/collections-and-installments#installment-deadlines)). `core/error.json` can carry `mutation_outcome`, so a buyer knows whether a failed state-changing request applied ([Mutation outcome](/docs/building/by-layer/L3/error-handling#mutation-outcome)).
- **Delegated composition (experimental).** A platform that owns the catalog can make `product_ids` the complete composable universe, and a seller that holds no inventory can declare `terms_only` finalize. See [Delegated composition](/docs/media-buy/product-discovery/delegated-composition).

### Delivery data offline sellers actually have

- **Spot lifecycle, makegoods, and break position (experimental).** `by_spot[]` rows can carry `spot_status` (`scheduled`, `aired`, `preempted`, `makegood`), `scheduled_at`, `replaces_spot_id`, and `break_position`. Sellers declare what they report, so a missing row is not read as non-delivery. See [Spot lifecycle](/docs/media-buy/media-buys/optimization-reporting#spot-lifecycle-makegoods-and-break-position).
- **Print proof of insertion and circulation (experimental).** `print_metrics` on `by_installment` rows reports the page and position delivered, circulation and its basis, and a tearsheet `evidence` record. See [Delivery evidence and circulation](/docs/creative/channels/print#delivery-evidence-and-circulation).
- **DOOH location and impression basis.** Concrete screens can carry structured `location`, and network products `venue_counts[]` ([DOOH](/docs/creative/channels/dooh#structured-location-for-planning-and-mapping)). Experimentally, placements, forecast points, and delivery rows say where a DOOH `impressions` figure comes from: `currency_measured`, `seller_modeled`, `sensor_measured`, or `hybrid`, with the audience multiplier applied to plays. Tiers are different units, so compare impressions within a tier only ([Impression basis](/docs/creative/channels/dooh#impression-basis-experimental)).
- **Installment lifecycle and proof of publication (experimental).** `by_installment[]` rows can carry `installment_status` and a `publication` record, so a creator post, newsletter edition, or podcast episode reports whether and where it ran. See [Installment lifecycle](/docs/media-buy/media-buys/optimization-reporting#installment-lifecycle-and-proof-of-publication).
- **Rows without impressions.** Delivery rows may omit `impressions` when the seller did not measure them, for example on rows that report plays or downloads instead. Absence means not measured, never zero, and sellers never omit it toward callers pinned below 3.3. See [Rows without impressions](/docs/media-buy/media-buys/optimization-reporting#rows-without-impressions).
- **Property-grain rollups and delivery projection.** `supports_property_breakdown` and `supports_installment_property_breakdown` commit a seller to `by_property` and `by_installment_property` rows. Top-level `by_package[]` rows can carry an advisory, experimental `projection` of lifetime impressions and spend ([Delivery projection](/docs/media-buy/task-reference/get_media_buy_delivery#delivery-projection)).
- **Audience sizes as ranges.** `sync_audiences` results can carry `audience_size` and `targetable_size` as bounded ranges with a `precision`. `matched_count` and `effective_match_rate` may now be absent, and buyers MUST NOT read absence as zero. See [Audience size](/docs/media-buy/task-reference/sync_audiences#audience-size).

### Linear TV, creators, and scheduled media

- **Minute-level dayparts (experimental).** A daypart entry can use `start_time` and `end_time` (`HH:MM`), and products declare the finest resolution they honor. A seller rejects a finer time and never rounds it. See [Minute-resolution dayparts](/docs/media-buy/advanced-topics/targeting#minute-resolution-dayparts-experimental).
- **Broadcast formats and currencies.** `demographic-system` gains `nmo` and `videoamp`. `video_hosted` gains the `mxf` container and broadcast mezzanine codecs, plus experimental `loudness`. The [broadcast guide](/docs/creative/channels/broadcast) states the reconciliation contract between as-run logs and audience data.
- **Installments on the compact lifecycle.** The canonical product that `list_products` and the proposal lifecycle read carries `installments[]`, so a proposal can name the creator and the slot, when it publishes, and its material deadlines. Experimentally, a buyer can ask for specific slots through `refine_proposals` and assign a creative to specific installments of a package. See [Installments in the compact lifecycle](/docs/media-buy/product-discovery/collections-and-installments#installments-in-the-compact-lifecycle).
- **Creator and collection cards (experimental).** Collections can carry images, sample content, and follower counts, talent can link to its brand identity, and responses can return full collection objects on request. See [Collection cards](/docs/media-buy/product-discovery/collections-and-installments#collection-cards-experimental).
- **Playback events and carousels.** `pixel_tracker` adds the quartile and `complete` playback events for hosted video and audio. `image_carousel` gains `card_image_sizes` and `cta_values`. See [Carousel ads](/docs/creative/channels/carousels#card-image-size).

### Proposals, offers, and signed terms

- **Open opportunities and later proposals (experimental).** A buyer can keep an opportunity open and let sellers send more proposals, within consent limits it sets. Sellers announce each with the identifiers-only `proposal.created` notification and serve them through [`list_proposals`](/docs/media-buy/task-reference/list_proposals). See [Open opportunities](/docs/media-buy/product-discovery/proposal-negotiation#open-opportunities-and-later-proposals).
- **Seller offers (experimental).** A seller can propose a change to an accepted buy, such as a postponed installment, a preemption, or under-delivery, as a committed proposal the buyer accepts, declines, or revises. Silence is never acceptance. See [Seller offers](/docs/media-buy/product-discovery/proposal-negotiation#seller-offers).
- **Signed terms bind every member.** `terms_digest` covers every member of `commercial_terms`, including members a party does not recognize. A party that cannot interpret one declines (`unrecognized_terms`) or rejects (`UNRECOGNIZED_TERMS`) instead of accepting. See [Verify terms independently](/docs/media-buy/product-discovery/proposal-negotiation#3-verify-terms-independently).
- **A stale terms digest has a code.** A seller refuses an `accept_proposal` whose `proposal_terms_digest` does not match the committed proposal, accepting nothing, and SHOULD return `PROPOSAL_TERMS_CHANGED` with `recovery: correctable`. See [Terms digest mismatch](/docs/media-buy/task-reference/accept_proposal#terms-digest-mismatch).
- **Renewal and replacement lineage (experimental).** A new buy can name the buy it succeeds with `predecessor_media_buy_id` and `lineage_reason`. The link is forward-only and same-account. See [Media Buy Lineage](/docs/media-buy/specification#media-buy-lineage).

### Accounts, principals, and agent identity

- **`request_account` (experimental).** Where a seller supports `account.requests`, `request_account` is the single account write: open an account, or change one's attributes. Each request either resolves in the same response or goes `in_review`, and a request that resolves to a different account than the one named says so. See [`request_account`](/docs/accounts/tasks/request_account).
- **A principal is the bound buyer agent.** `principal_kind` and `expected_principal_kind` are deprecated, because a bound principal is always `buyer_agent`.
- **Reporting subscriptions on the principal (experimental).** `sync_principal` takes `reporting_subscriptions`: one registration per feed purpose, across every authorized account or named ones, with coverage a buyer can compute from the wire. Subscriptions can break delivery down by geography the same way a delivery report does. See [Reporting subscriptions](/docs/protocol/sync_principal#reporting-subscriptions).
- **Agent identity and buyer self-onboarding (experimental).** The Web Bot Auth signing profile identifies the signer by its origin and verifies against that origin's key directory, with no capabilities call and no seller-issued credential. Operators list their agents in `trust.json`, brands publish grants there, and sellers publish their onboarding posture in `account.agent_onboarding`. The RFC 9421 profiles are deprecated and work through 3.x. See [A buyer agent onboards itself](/docs/accounts/buyer-agent-self-onboarding) and the [agent identity migration guide](/docs/reference/migration/agent-identity-3-3).

### Schemas open by default, and what left 3.3

**Schemas are open by default ([DR-0036](https://github.com/adcontextprotocol/adcp/blob/main/governance/decisions/DR-0036-closed-schemas-stay-closed-within-a-major.md)).** Closing a schema only breaks validators that hard-code it, so 3.3 opens the schemas that were meant to be open: 744 of the 859 closed locations. 115 stay closed, most for a structural reason such as unions told apart by key presence, join keys, privacy clamps, and `trust.json`. The nodes inside `commercial_terms`, with `proposal-budget-constraint`, are held closed until 4.0. Every payload that was valid stays valid, but generated types change: TypeScript types gain index signatures, Pydantic models stop forbidding extra fields, and Zod validators accept unknown keys. A strict validator built from 3.2.10 or earlier still rejects 3.3 fields, so send them only to 3.3 peers. 3.2.11 opens the same locations in 3.2. See [Schemas are open by default](/docs/reference/migration/3-2-to-3-3#schemas-are-open-by-default).

**The rules for what changes between releases.** The [versioning page](/docs/reference/versioning) opens with them. A minor only adds. A replaced field is emitted alongside its replacement until the next major. Removals and breaking changes happen in a major. A field stays off a mutating request in a minor when an older seller that ignored it would commit to something different, unless it ships behind a capability the seller declares.

**What left 3.3.** Opening the schemas settled which beta features stay. Features withdrawn only because their schema was closed stay. Fields the betas added to deprecated tasks leave, and the live tasks keep those features. Fields that would extend the commercial terms wait for 4.0 ([below](#withdrawn-from-3-3-planned-for-4-0)). The [migration guide](/docs/reference/migration/3-2-to-3-3#closed-schema-triage-what-stays-in-3-3) lists every field.

**Smaller schema changes.** Six enum values that an SDK target language reserves gain a replacement, and the originals are deprecated: `pass` → `passed`, `global` → `all`, and `name` → `full_name` ([Reserved-word-safe enum replacements](/docs/reference/migration/3-2-to-3-3#reserved-word-safe-enum-replacements)). The single-value form of 17 scalar-or-list unions is deprecated, so senders send a one-item array. A payload that matched two branches of a `oneOf`, and so failed, now resolves to one branch; nothing that validated before stops validating. A seller MUST reject a creative manifest without `format_option_ref` when two or more of the product's `format_options` share its `format_kind`.

### Tightened rules

These narrow what a conformant implementation may do. Each is detailed in the [migration guide](/docs/reference/migration/3-2-to-3-3#required-to-claim-3-3-behavior) and recorded in [Versioning and governance](/docs/reference/versioning#3-3-exceptions-to-3-x-compatibility).

- **Discovery never provisions an account.** Discovery and negotiation tasks MUST NOT create or activate an account or accept default terms. See [Account references before provisioning](/docs/accounts/overview#account-references-before-provisioning).
- **One agent-resolution rule.** Request signing, webhook signing, governance JWS `iss`, designated-task response signing, and rights attestations share one algorithm for which brand.json lists an agent and which keys it may sign with. Some signatures that verified under 3.2 now fail. See [Agent resolution](/docs/building/by-layer/L1/security#agent-resolution).
- **`required_for` over A2A, hardened.** The A2A operation-resolution hardening clauses were SHOULD in 3.2.x and are MUST from 3.3. Verifiers declare support with `request_signing.operation_sources`. See [Operation resolution over A2A](/docs/building/by-layer/L1/security#operation-resolution-over-a2a).
- **`reporting_webhook.operation_id` fails closed.** The seller echoes it into every `media_buy_delivery` webhook and sends none to a registration that omits it. See [Reporting webhooks](/docs/building/by-layer/L3/webhooks#reporting-webhooks).
- **Responses conform to the served release.** A seller that lists 3.3 or later in `supported_versions` serves each listed release's published schema, `get_adcp_capabilities` and webhook payloads included ([DR-0024](https://github.com/adcontextprotocol/adcp/blob/main/governance/decisions/DR-0024-responses-conform-to-served-release.md)).
- **Every task response carries the envelope.** Each task response composes `core/protocol-envelope.json`, and `status` is required. A task-level `message` over 2,000 characters is truncated, never a failure.
- **Seller revisions advance on every committed change**, whatever its origin, including `sync_creatives` assignments and connected-platform changes. Buyers that send a stale `revision` see more `CONFLICT`; that is intended ([DR-0031](https://github.com/adcontextprotocol/adcp/blob/main/governance/decisions/DR-0031-seller-revision-any-origin.md)).
- **Sellers accept creatives that conform to the declared format option**, and enforce only the limits they declared. See [Format conformance](/docs/creative/task-reference/sync_creatives#format-conformance).
- **Sellers declare the assignment operations they accept** in `creative.assignment_operations`, and reject any other with `UNSUPPORTED_FEATURE`. A `replace` carries the replaced assignment's settings to the replacement. See [Which operations a seller accepts](/docs/creative/task-reference/sync_creatives#which-operations-a-seller-accepts).
- **A major-only request is served the oldest supported release** in that major, 3.0 where supported ([DR-0034](https://github.com/adcontextprotocol/adcp/blob/main/governance/decisions/DR-0034-major-only-requests-are-served-the-oldest-release.md)). Send `adcp_version` to get newer behavior.
- **Campaign governance rules are settled (experimental).** A failed `approved_sellers` or `delegations` evaluation is a `denied` verdict in every governance mode, a caller that cannot access a plan gets `PLAN_NOT_FOUND`, a budget cut below committed spend is rejected, and a plan that requires human review escalates in every mode. See the [campaign governance specification](/docs/governance/campaign/specification).
- **Also:** advertise only the measurement terms you accept, keep `uid2` and `euid` identifiers in their raw wire form, bound counterparty-asserted domain lists, emit platform IDs under both names, enforce lowercase hostname formats on property domain identifiers, resolve property list references through `get_property_list`, and omit flat totals for metrics reported under more than one qualifier set.

Some guarantees loosen. The brand.json cap rises to 2 MiB, a `ready` audience no longer promises match counts, `media_buy.audience_targeting` no longer promises inline member push, an origin-only `authorized_agents[].url` authorizes the agent at any path on that origin, and `reporting_webhook.authentication` becomes optional on 3.3 requests. A 3.2 peer can reject what a 3.3 peer accepts in each case; see [Send only to 3.3 peers](/docs/reference/migration/3-2-to-3-3#send-only-to-3-3-peers).

### Bounded responses

A seller agent that answers a discovery call with tens of megabytes is an availability attack on every buyer that reads the body before checking its size. Clients SHOULD bound every AdCP response they read, enforce the bound while the body is received, and surface an oversized response as an error rather than truncating it. The default is 4 MiB. Receivers of A2A push notifications and AdCP webhooks SHOULD bound the inbound body the same way, before signature verification. Capabilities are bounded by structure: every array, string, and keyed map in `get_adcp_capabilities` has a limit, and agents MUST NOT design to a byte figure. See [Response size bounds](/docs/building/by-layer/L1/security#response-size-bounds) and [Discovery responses stay small](/docs/building/concepts/managing-response-size#discovery-responses-stay-small).

### Optional declarations

Sellers can declare catalog ingestion limits (`catalog_ingestion`), the delivery types they sell (`supported_delivery_types`), match keys for cross-publisher frequency capping (experimental), whether they push audience members, assignment landing pages and trackers, event source archive, and SDK implementation metadata (`adcp.implementation.sdks[]`). Signals can carry `age_determination_bases`. `ext.adcp` is a registered AdCP-owned extension namespace. Each is optional, and a buyer reads absence as "not declared". The full list is in the [release notes](/docs/reference/release-notes#3-3-feature-index).

### Two kinds of sell-side agent (non-normative)

A sales agent does two jobs: it faces buyers, and it faces the inventory. 3.3 doesn't change the protocol for this, but it is worth knowing before you build. A **storefront** agent answers briefs, proposes, negotiates, and packages, and books by calling inventory agents as their buyer. An **inventory** agent holds the catalogue and avails, executes buys, and reports delivery. Today's sales agent plays both roles. See [Storefront and inventory roles](/docs/building/operating/seller-integration#storefront-and-inventory-roles) for how to split them with the tasks you already have. Standardizing the roles is proposed for 4.0 in [#8993](https://github.com/adcontextprotocol/adcp/issues/8993).

### Conformance

- **Fixed-rate certification.** The `sales_fixed_rate` storyboard grades the stable `sales-fixed-rate` specialism, and a passing claim counts toward the AAO Verified media-buy badge.
- **Broadcast TV certification.** `sales-broadcast-tv` 1.1.0 certifies one authorized TV transaction on a guaranteed or a non-guaranteed fixed-price path. Claims graded on 1.0.x have a grace window.
- **New storyboards** grade holds, account requests, reporting-subscription coverage, declared format-option acceptance, `replace` settings transfer, and a mismatched terms digest on `accept_proposal`.
- **Badges.** 3.3 badges are issued once hosted grading moves to the `3.3.0` compliance bundle, graded against `3.3.0` with a `"3.3"` advertisement and response echo. Runs against a 3.3 beta or release candidate stay diagnostic. See [AAO Verified](/docs/building/verification/aao-verified).

## Experimental surfaces in 3.3

3.3 adds more than thirty experimental surfaces, among them holds, open opportunities, seller offers, spot lifecycle, print metrics, DOOH impression basis, live creative updates, `request_account`, reporting subscriptions, match keys, and the Web Bot Auth profile. No experimental surface graduates in 3.3. To use one, inspect `experimental_features` and pin an exact release. The per-surface table, with what may change next, is in the [release notes](/docs/reference/release-notes#experimental-surfaces-in-3-3), and the contract is in [experimental status](/docs/reference/experimental-status).

Two notices take effect with 3.3.0:

- **Creative evaluator.** The experimental `build_creative.evaluator` drops its `evaluator_id` source form and withdraws the `list_evaluators` follow-on. Use inline `exemplars` or an allowlisted `agent_url` ([migration](/docs/reference/migration/3-2-to-3-3#experimental-creative-evaluator-drops-evaluator_id)).
- **Reliable Reporting.** 3.3.0 is the first minor after November 20, 2026, so a seller may now compact older superseded snapshots. Persist any snapshot rows you need ([notice](/docs/reference/migration/3-2-to-3-3#superseded-reporting-snapshots-may-be-compacted)).

## Withdrawn from 3.3, planned for 4.0

These shipped in a 3.3 beta or release candidate and are not part of 3.3.0. Each adds terms to `commercial_terms`, or changes how a signed term is read, and `commercial_terms` is held closed until 4.0. A buyer must not be bound by terms it cannot read. 4.0 gives `commercial_terms` a declared extension point with must-understand and brings them back ([adcp#8501](https://github.com/adcontextprotocol/adcp/issues/8501)).

| Feature | Shipped in |
|---|---|
| Definition pins (`commercial_terms.definition_pins[]`, `REFERENCE_DEFINITION_CHANGED`) | `3.3.0-beta.0` and `3.3.0-beta.1` |
| Purchase rights (`purchases[].rights[]`) | `3.3.0-beta.1` |
| Installment selection on the purchase (`purchases[].installments[]`) | `3.3.0-beta.1`. The request side returns as experimental installment refinement. |
| Selection-dependent `price_adjustments`, `counting_mechanisms` on measurement terms, and `target_audiences` | `3.3.0-beta.1` through `3.3.0-beta.5` |
| `metric_id` on performance standards | `3.3.0-beta.1` through `3.3.0-rc.0` |

The designs are kept in [Planned for 4.0](/docs/reference/migration/v4-compatibility#planned-for-4-0-withdrawn-from-3-3).

## Deprecations

Each keeps working throughout 3.x and is expected to be removed in 4.0:

- `seller_id` on event source and audience results (use `platform_id`; send both);
- the natural-key account reference after provisioning, and the account identity-rekey machinery: `account.identity_updates`, `operator_identity`, `ACCOUNT_MOVED`, `ACCOUNT_IDENTITY_CONFLICT`, and `account.stable_account_id`;
- `principal_kind` and `expected_principal_kind`;
- the RFC 9421 request- and webhook-signing profiles (use the experimental Web Bot Auth profile), and condition (b) of `request_signature_required`;
- the boolean form of `demographics` (send `{ "age": true }`);
- six reserved-word enum values, and the single-value form of the scalar-or-list unions (the `brand.json` color values stay until 5.0).

See [Deprecations](/docs/reference/migration/3-2-to-3-3#deprecations).

## What to change when you adopt 3.3

| If you are… | Before advertising or sending `"3.3"` |
|---|---|
| Any seller or service | Advertise `"3.3"` only when you serve it, and serve each release you list with that release's schema. Compose the protocol envelope on every response. Advance seller revisions on every committed change. |
| A seller that provisions accounts | Return and accept `account_id` everywhere, never change it, and never provision on a discovery task. |
| A buyer | Store `account_id` and send it. Gate 3.3-only fields on the negotiated version. Expect `CONFLICT` after seller-side changes, and re-read before retrying. Treat a missing `impressions` as not measured. |
| A signing or verifying implementation | Resolve agents by canonical URL, publish every pinned key in your JWKS, apply the A2A hardening clauses, and raise the brand.json cap to 2 MiB. |
| A seller sending delivery webhooks | Echo `reporting_webhook.operation_id`, and send nothing to a registration without one. |
| A seller with a creative library | List the assignment operations you accept, accept creatives that conform to the declared format option, and reject a manifest without `format_option_ref` where two format options share a `format_kind`. |
| A linear TV, print, or DOOH seller | Adopt the delivery fields you can populate; gate 3.3-only rows and fields on the negotiated version. |
| A seller or SDK built from a beta or release candidate | Drop the fields that left 3.3 and use the renamed experimental values; see the [3.3 prerelease history](/docs/reference/3-3-beta). |
| An SDK maintainer | Generate from the signed `3.3.0` tarball, not `main`, and check the [SDK-facing changes](/docs/reference/migration/3-2-to-3-3#sdk-and-code-generator-maintainers), including the opened schemas. |

**SDKs.** TypeScript `@adcp/sdk@17.0.0` ships alongside `3.3.0` and embeds it, on the npm `latest` and `adcp-3.3` dist-tags; `adcp-3.2` stays on the 16.7.x line. Python `adcp==10.0.0` embeds the same bundle and can follow the protocol release by a few days. A Python integration stays on `"3.2"` with `adcp` 9.x until it is published: each 10.0.0 prerelease negotiates only its own 3.3 prerelease pin, which a 3.3.0 peer does not list. Go and Java do not support 3.3; use raw-wire calls against the signed bundle. `@adcp/sdk` 17 is a major release, so read its [16 to 17 migration guide](https://github.com/adcontextprotocol/adcp-client/blob/main/docs/migration-16-to-17.md) first. See [Choose your SDK](/docs/building/by-layer/L4/choose-your-sdk).

**Support.** 3.3.x gets full support for at least 12 months after 4.0 GA. 3.2.x gets security and critical fixes only, and 3.1.x and 3.0.x get security fixes only. See [Versions & Compatibility](/docs/reference/versions).
