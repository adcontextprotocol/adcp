<Warning>
**Experimental breaking-change notice published October 26, 2026.** Under AdCP's six-week [experimental-surface notice policy](/docs/reference/experimental-status#contract-for-experimental-surfaces), the renames below must not appear in an immutable release before **December 7, 2026**. AdCP 3.3 ships the principal layer under its current names; the only 3.3 changes are this notice, the vocabulary below, and the deprecation of `principal_kind`. Tracked in [#8280](https://github.com/adcontextprotocol/adcp/issues/8280).
</Warning>

## Why

The principal layer (`protocol.principal`) is the seller's record of the calling buyer agent: who it was resolved to, its relationship with the seller, and the webhooks, reporting destinations, and declarations it configured. Since the 3.3 agent identity work, a principal is always one bound buyer agent, keyed by its stable subject (the canonical Agent URL for RFC 9421 signers, the canonical origin for Web Bot Auth signers). The word has no other meaning left in AdCP:

- `principal_kind: operator` described a person or operator login calling a seller directly. No deployment uses it. When an agent holds an operator's credential for a platform that owns its account namespace, the account access belongs to the credential, and the agent is still the caller.
- The operators an agent acts for are facts on its accounts, never principals.
- "Principal" is security jargon that appears in no other task name. In an MCP tool list, `get_principal` tells neither a developer nor a model what it returns.

The buyer agent always reads its own record, so the new names say what is read and whose it is. `buyer_agent` also keeps the name apart from `sync_agent_notification_configs`, where "agent" means the seller.

## What changes in 3.3

Nothing on the wire. AdCP 3.3:

- defines a principal as the buyer agent as the seller has bound it, and nothing else;
- deprecates `principal_kind` on `get_principal` and `sync_principal` responses, `expected_principal_kind` on `sync_principal` requests, and the `enums/principal-kind.json` enum. Sellers keep sending `principal_kind` until the rename lands; a bound buyer agent is always `buyer_agent`;
- publishes the mapping below.

## What changes when the rename lands

Names change only for callers pinned at or above the release that carries the rename. Callers pinned below it keep the 3.3 names, and a seller serves each caller the names of its pin, as it already does for other version-gated fields.

| 3.3 name | New name |
|---|---|
| `sync_principal` | `sync_buyer_agent_config` |
| `get_principal` | `get_buyer_agent_config` |
| `adcp.principal` capability block | `adcp.buyer_agent_config` |
| `adcp.principal.sync_task` / `read_task` values | `sync_buyer_agent_config` / `get_buyer_agent_config` |
| `principal.changed` notification type | `buyer_agent_config.changed` |
| `protocol.principal` experimental feature id | `protocol.buyer_agent_config` |
| `principal_id` | `buyer_agent_id` (the seller's record ID, not the agent URL) |
| `principal_kind`, `expected_principal_kind` | removed |
| `core/principal-state.json` | `core/buyer-agent-config-state.json` |
| `core/principal-declarations.json`, `core/principal-declarations-state.json` | `core/buyer-agent-declarations.json`, `core/buyer-agent-declarations-state.json` |
| `core/principal-relationship.json`, `enums/principal-relationship-status.json` | `core/buyer-agent-relationship.json`, `enums/buyer-agent-relationship-status.json` |
| `core/principal-changed-webhook.json` | `core/buyer-agent-config-changed-webhook.json` |
| `sync_agent_notification_configs` | deprecated; use `notification_configs` on `sync_buyer_agent_config` |

Behavior does not change: identity resolution, binding, relationship status, the version fence, destination proof, suspension, and the webhook payload all stay as they are.

## Before and after

Capability declaration, 3.3:

```json
{
  "experimental_features": ["protocol.principal"],
  "adcp": {
    "principal": {
      "supported": true,
      "sync_task": "sync_principal",
      "read_task": "get_principal",
      "caller_event_types": ["capabilities.changed", "principal.changed"]
    }
  }
}
```

After the rename, for callers pinned at the new release:

```json
{
  "experimental_features": ["protocol.buyer_agent_config"],
  "adcp": {
    "buyer_agent_config": {
      "supported": true,
      "sync_task": "sync_buyer_agent_config",
      "read_task": "get_buyer_agent_config",
      "caller_event_types": ["capabilities.changed", "buyer_agent_config.changed"]
    }
  }
}
```

Read result, 3.3:

```json
{
  "status": "completed",
  "result": {
    "kind": "recognized",
    "principal_kind": "buyer_agent",
    "principal_id": "prin_01K4C6RGT5Q18VCPGXE7DDWQ5F"
  }
}
```

After:

```json
{
  "status": "completed",
  "result": {
    "kind": "recognized",
    "buyer_agent_id": "prin_01K4C6RGT5Q18VCPGXE7DDWQ5F"
  }
}
```

The ID value doesn't change; only the field name does.

## What to do now

- **Sellers:** keep the 3.3 names. Plan to serve both sets by caller pin once the rename lands. Don't build new behavior on `principal_kind: operator`; it goes away with the field.
- **Buyers and SDKs:** stop branching on `principal_kind` and stop sending `expected_principal_kind`. Route on the task names a seller advertises in `sync_task` and `read_task`, not on hard-coded names, so the switch is a capability change.
