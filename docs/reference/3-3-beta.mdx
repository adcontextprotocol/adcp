# AdCP 3.3 beta program

<Warning>
**Use the beta in development and staging, not production.** New production integrations should stay on AdCP 3.2 until 3.3 reaches general availability. Every beta is an immutable checkpoint, but later betas may change 3.3 surfaces before GA.
</Warning>

3.3 is a minor release with a deliberately short cycle. Its beta follows the same order as 3.2: the protocol first, then the SDKs.

## Beta status

The latest checkpoint is **`3.3.0-beta.5`, published 2026-11-07**. Each beta is an immutable, signed checkpoint, and later betas may change 3.3 surfaces before GA. GA follows the first beta that meets every one of the GA criteria in [#8600](https://github.com/adcontextprotocol/adcp/issues/8600): SDK support for the latest beta, green storyboards, the closed-schema triage ([#8501](https://github.com/adcontextprotocol/adcp/issues/8501)), no open objections on consent items and decision records, and current release docs. The criteria stand as written: their consent closed on 2026-11-07 with no objections. The closed-schema triage lands after its own consent closes on 2026-11-13, and the GA-candidate beta follows in the week of 2026-11-16.

| Checkpoint | Published | Purpose | Who should test |
|---|---|---|---|
| `3.3.0-beta.0` | 2026-10-22 | Canonical schemas, compliance assets, skills, and protocol manifest for SDK implementation | SDK maintainers, code-generator maintainers, raw-wire implementers, and agent teams that can validate without generated 3.3 SDK types |
| `3.3.0-beta.1` | 2026-10-29 | Beta.0 integration corrections, the account identity model, `request_account`, principal-level reporting subscriptions, undisclosed rosters, and the first commercial experiments | Buyer and seller teams running end-to-end integrations, and SDK maintainers ingesting the bundle |
| `3.3.0-beta.2` | 2026-10-30 | Account change outcomes, seller offers, measurement provenance, structural capability bounds, the principal clarification, reporting-subscription convergence, and the withdrawal of definition pins, purchase rights, and installment selection | The same teams, against the withdrawn surfaces removed |
| `3.3.0-beta.3` | 2026-10-31 | Live creative updates, the protocol envelope on every task response, money terms on resolved account requests, revocation as no access, and reporting-subscription coverage computable from the wire | The same teams |
| `3.3.0-beta.4` | 2026-11-05 | Reporting-subscription coverage fixes (per-package `added_at`, a reduced grant as a loss of authority) and the probe reset, `replace` that transfers assignment settings, tracker-slot limits only where a format declares slots, `BUDGET_TOO_LOW` details, `creative.supports_provenance`, `opportunity` on explicit-package buys, undefined-property reporting, and the hold, account-request, and reporting-subscription storyboards | The same teams, and SDK maintainers adopting the two coverage rule changes |
| `3.3.0-beta.5` | 2026-11-07 | Experimental match keys for cross-publisher frequency capping, `sales-fixed-rate` promoted to stable, and the bundled Public Suffix List (DR-0037) | The same teams; this is the checkpoint the docs describe |

Beta.0 did not wait for the SDKs. A checkpoint is SDK-backed only after the matching SDK versions and integration evidence are published. `@adcp/sdk` 17.0.0-beta.11 is the first published SDK that bundles beta.3 ([SDK guidance](#sdk-guidance)). Three features that shipped in the betas are [withdrawn after beta.1](#withdrawn-after-beta-1).

`@adcp/sdk` 17.0.0-beta.18 through 17.0.0-beta.20 and Python `adcp` 10.0.0b12 support beta.4. `@adcp/sdk` 17.0.0-beta.21 and later support beta.5, and Python adoption of beta.5 is in flight ([SDK guidance](#sdk-guidance)).

## Know which version string to use

The artifact version, wire pin, and documentation selector are related but not interchangeable:

| Surface | beta.0 | beta.1 | beta.2 | beta.3 | beta.4 | beta.5 |
|---|---|---|---|---|---|---|
| Protocol artifact | `3.3.0-beta.0` | `3.3.0-beta.1` | `3.3.0-beta.2` | `3.3.0-beta.3` | `3.3.0-beta.4` | `3.3.0-beta.5` |
| Git tag | `v3.3.0-beta.0` | `v3.3.0-beta.1` | `v3.3.0-beta.2` | `v3.3.0-beta.3` | `v3.3.0-beta.4` | `v3.3.0-beta.5` |
| `adcp_version` wire pin | `"3.3-beta.0"` | `"3.3-beta.1"` | `"3.3-beta.2"` | `"3.3-beta.3"` | `"3.3-beta.4"` | `"3.3-beta.5"` |
| Documentation selector | `3.3-beta` | `3.3-beta` | `3.3-beta` | `3.3-beta` | `3.3-beta` | `3.3-beta` |

Only send a prerelease wire pin to a peer that advertises that exact value in `get_adcp_capabilities.adcp.supported_versions`. Prerelease pins are exact: a buyer pinned to `"3.3-beta.4"` must not silently negotiate to beta.5, and a stable `"3.2"` pin must not silently negotiate to a beta.

## Test a beta without an SDK

Download the signed protocol bundle of the beta you test (the commands use the latest, `3.3.0-beta.5`; substitute another published checkpoint) rather than copying schemas from `main` or from the moving `/schemas/latest/` path:

```bash
curl -fLO https://adcontextprotocol.org/protocol/3.3.0-beta.5.tgz
curl -fLO https://adcontextprotocol.org/protocol/3.3.0-beta.5.tgz.sha256
shasum -a 256 -c 3.3.0-beta.5.tgz.sha256
tar -xzf 3.3.0-beta.5.tgz
```

The extracted `adcp-3.3.0-beta.5/` directory contains:

- `manifest.json`: release version, bundle contents, skills, and file count;
- `schemas/`: source-shaped and bundled request/response schemas, including `schemas/manifest.json` for the task and capability inventory;
- `compliance/`: storyboards, test kits, vectors, and runner contracts;
- `skills/`: role guidance for coding agents;
- `openapi/`: published OpenAPI artifacts.

Verify the Sigstore signature before using the bundle as a build input. See [Verifying protocol tarballs](/docs/reference/verifying-protocol-tarballs) for the certificate-identity and issuer checks.

Useful tests are:

1. Generate or refresh types from the pinned bundled schemas.
2. Validate representative requests and responses for the roles you implement, including the new 3.3 surfaces you plan to adopt: the `account_id` identity model and, if you support it, `request_account`; `status` on every response through the protocol envelope; `expected_confirmation_at`, vendor-metric `outcome_target` goals, `reporting_webhook.operation_id`, `media_buy.features.catalog_ingestion`, the DOOH `location` and `dooh_inventory_summary` fields, `sync_audiences` audience sizes, and the experimental spot, print, daypart, loudness, reporting-subscription, live-creative-update, match-key, and governance `budget.periods[]` fields.
3. Compare your advertised tools with `schemas/manifest.json`.
4. Exercise raw MCP or A2A calls with `adcp_version: "3.3-beta.5"` against a staging peer that advertises the same pin.
5. Run the compliance assets with a source-compatible runner if you maintain one. Do not weaken production authentication to accommodate a beta runner.

## Try the preview on the public test agent

The public test agent at `https://test-agent.adcontextprotocol.org` serves `3.3.0-beta.5` as an opt-in preview alongside its stable releases. It lists `"3.3-beta.5"` in `adcp.supported_versions` and serves the preview only to a request that pins exactly that value:

| Request | Served |
|---|---|
| `adcp_version: "3.3-beta.5"` | The preview. Responses echo `"3.3-beta.5"` and validate against the published `3.3.0-beta.5` schemas. |
| `adcp_version: "3.2"`, `"3.3"`, or a later release | 3.2. A release pin never resolves onto a prerelease. |
| Any other 3.3 prerelease, such as the earlier preview `"3.3-beta.4"` | Never the preview. Prerelease pins match exactly. |
| `adcp_major_version` alone, or no version | The route's stable default, never the preview. |

```bash
curl -s https://test-agent.adcontextprotocol.org/sales/mcp \
  -H "Authorization: Bearer $ADCP_AUTH_TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_adcp_capabilities","arguments":{"adcp_version":"3.3-beta.5"}}}'
```

At the preview pin, `/sales/mcp` serves the experimental 3.3 surfaces the training agent implements:

- account requests (`account.requests`): `request_account`, and `account_requests` on `list_accounts`;
- the caller's `authorization`, with `authorized_at` and `regranted_at`, and `revision` on each `list_accounts` account;
- principal-level reporting subscriptions (`media_buy.reporting_subscriptions`): the `reporting_subscriptions` section of `sync_principal` and `get_principal`, and `subscription_coverage` on `get_reporting_status`;
- the `reporting_subscription_probe` controller scenario, which revokes, reduces, and restores grants and advances a per-caller sandbox clock;
- collection cards (`media_buy.collection_cards`): `include_collections` on `get_products`, `list_products`, `request_proposals` and `refine_proposals`, with images, samples, links, talent `brand_ref` and follower counts on the CreatorLoop creator channels;
- the collection catalog (`media_buy.collection_catalog`): `list_collections`, and the `collection_card.*` and `collection_catalog.bulk_change` webhooks registered through `sync_accounts`;
- the `seed_collection` controller scenario, which changes the caller's cards (a sample, a removal, a follower sweep) so the card webhooks fire;
- inventory holds ([Hold policy](/docs/media-buy/task-reference/refine_proposals#hold-policy-experimental)): `hold_policy` on products and drafts (`media_buy.hold_policy`), committed proposals with `hold_placed_at`, ranked holds with `hold_rank` (`media_buy.hold_ranking`), per-installment `holds` (`media_buy.installment_holds`), `extend_hold` (`media_buy.hold_extension`), and the `force_hold_unavailable` controller scenario.

At the same pin, `/brand/mcp` returns `collections` on `get_brand_identity` for the creators (`brand.collection_links`).

Holds are kept per caller and timed by the caller's sandbox clock, so two accounts that hold the same slot are queued at positions 1 and 2. These products carry hold policies:

| Product | Hold policy |
|---|---|
| `crestline_radio_premium` | Exclusive, 1 to 3 days. A second buyer gets `hold_unavailable` while a hold stands. |
| `streetlevel_premium` | Ranked, 2 to 7 days. While a hold ahead stands, accepting a hold behind it returns `PRODUCT_UNAVAILABLE`. |
| `beacon_search_standard` | Not holdable. A draft that allocates it finalizes as terms only. |
| `trendsettr_premium` | Exclusive, 1 to 3 days, extendable to 10 days in total. |
| `creatorloop_creator_*` | Ranked, 2 to 5 days, extendable to 21 days in total, never past the slot's booking deadline. Each upcoming slot is held separately and listed in `holds`. |

Other products take the default: a hold that never contends.

`tools/list` includes `request_account` and `list_collections` only when the listing is pinned to the preview (`params._meta.adcp_version`, as `@adcp/sdk` sends it).

With `@adcp/sdk`, use 17.0.0-beta.21 or later, which negotiates exactly `3.3-beta.5`. Earlier 17.0.0 betas negotiate an older beta, so they settle on 3.2 with the test agent.

<Warning>
**The preview is experimental and can change without notice.** It follows the 3.3 beta that the current `@adcp/sdk` prerelease negotiates, so it can trail the latest published beta, and it moves when the SDK does. Once it moves, the old pin is no longer served. AAO can also switch the preview off, after which the agent serves only its stable releases. Use it to try 3.3 surfaces, not as a stable integration target.
</Warning>

<Note>
**No 3.3 verification badge is issued from a beta.** A beta bundle is an implementation input, not a certification target, and prerelease grading runs are diagnostic, as they were for 3.2.
</Note>

## SDK support contract

An SDK support claim must name all of the following:

- exact SDK package version;
- exact AdCP prerelease bundle used to generate or load schemas;
- supported roles and transports;
- known unsupported or raw-only surfaces;
- install command and one tested validation command.

The SDK compatibility matrix lives in [Choose your SDK](/docs/building/by-layer/L4/choose-your-sdk). Until a row names support for a beta, treat that SDK's generated 3.3 types and validators for it as unavailable. Raw JSON calls may still be possible, but they are not equivalent to SDK support.

SDK maintainers should report protocol ambiguities against the [AdCP repository](https://github.com/adcontextprotocol/adcp/issues). Report SDK implementation bugs in the SDK's own repository. Accepted protocol fixes receive a changeset and ship in the next beta; a published beta is never rebuilt in place.

## SDK guidance

**TypeScript.** Use `@adcp/sdk` **17.0.0-beta.6 or later** (npm `beta` dist-tag) to test 3.3. The published prereleases bundle a signed AdCP release: 17.0.0-beta.6 bundles `3.3.0-beta.1`, 17.0.0-beta.10 bundles `3.3.0-beta.2`, 17.0.0-beta.11 through 17.0.0-beta.17 bundle `3.3.0-beta.3`, 17.0.0-beta.18 through 17.0.0-beta.20 bundle `3.3.0-beta.4`, and 17.0.0-beta.21 and later bundle `3.3.0-beta.5`. Each negotiates only its own beta, so a buyer and seller on different betas settle on a stable release. Pin the exact SDK version, and send a prerelease `adcp_version` only to a peer that advertises that exact pin. `@adcp/sdk` 17 is a major release; read its [16 to 17 migration guide](https://github.com/adcontextprotocol/adcp-client/blob/main/docs/migration-16-to-17.md) first.

**Python.** `adcp` **10.0.0b12**, a PyPI prerelease (`pip install adcp==10.0.0b12`), adopts the signed `3.3.0-beta.4` bundle. `adcp` 10.0.0-beta.13, which adopts `3.3.0-beta.5`, is tagged but not yet on PyPI. Keep production-line work on the `adcp` 3.2 release.

**Go.** Check the [adcp-go releases](https://github.com/adcontextprotocol/adcp-go/releases) for a published 3.3 support statement; this page names none.

Do not combine an SDK that bundles an earlier beta with a later wire pin unless that SDK explicitly documents forward compatibility. GA needs SDK support for the latest beta, so these versions will move; [Choose your SDK](/docs/building/by-layer/L4/choose-your-sdk) is the SDK matrix, and it can lag the npm dist-tag.

## SDK convergence

A beta is the SDK-backed ecosystem checkpoint only when:

- every first-party SDK's support for it is marked supported, partial, or unavailable with an exact package version;
- accepted protocol feedback from the previous beta is merged;
- the integration scenarios below have run against the previous beta and identify any correction in the candidate;
- copy/paste installation and validation commands have been executed as published;
- the cumulative migration guide and release notes describe any correction that requires adopter action.

After a beta is published, SDK maintainers ingest that signed bundle and publish an exact support statement or an explicit unsupported or partial result. Only after the matching buyer and seller scenarios pass is that beta the SDK-backed checkpoint.

## Withdrawn after beta.1

Three features shipped in `3.3.0-beta.1` and are not part of 3.3. They leave the protocol after beta.1. All three add terms to `commercial_terms`, which stays closed within 3.x so that a buyer is never bound by terms it cannot read ([adcp#8501](https://github.com/adcontextprotocol/adcp/issues/8501)). They are planned for 4.0, where `commercial_terms` gets a declared extension point with must-understand.

| Feature | Shipped in | Action |
|---|---|---|
| Definition pins: `commercial_terms.definition_pins[]`, the `definition_changed` reason, `drifted_pins[]`, `REFERENCE_DEFINITION_CHANGED`, the `definition_pin_probe` scenario, and the `definition_pin_drift` storyboard ([#7960](https://github.com/adcontextprotocol/adcp/pull/7960)) | beta.0 and beta.1 | Stop emitting and requiring them. A seller that emits pins to a peer on the later schema sends a field a closed `commercial_terms` rejects. The beta rule that sellers pin covered definitions no longer applies. |
| Purchase rights (`media_buy.purchase_rights`): `purchases[].rights[]`, `brand/rights-scope.json`, and the `paid_amplification` and `content_reuse` values of `right-use` ([#8101](https://github.com/adcontextprotocol/adcp/pull/8101)) | beta.1 | Stop listing the feature id and emitting `rights[]`. Carry rights through `acquire_rights` until 4.0. |
| Installment selection (`media_buy.installment_selection`): `purchases[].installments[]` and `refine_proposals` `installment_changes` ([#8246](https://github.com/adcontextprotocol/adcp/pull/8246)) | beta.1 | Stop listing the feature id and emitting or accepting the fields. Installments on the canonical product and `holds[]` stay. |

The [migration guide](/docs/reference/migration/3-2-to-3-3#withdrawn-from-3-3-planned-for-4-0) lists every surface removed, and [Planned for 4.0](/docs/reference/migration/v4-compatibility#planned-for-4-0-withdrawn-from-3-3) keeps the designs.

## Required integration evidence

Retain the exact protocol bundle, SDK package versions, capability responses, redacted requests and responses, task IDs, and account and MediaBuy identifiers for each run.

1. **Account lifecycle.** Call a discovery task (`get_products` or `list_products`) with a buyer-declared natural key that was never provisioned. The seller returns `ACCOUNT_NOT_FOUND` (a seller that provisions lazily instead of exposing `sync_accounts` may answer without creating the account), and `list_accounts` shows no new account. Then provision, with `sync_accounts` or the seller's lazy path on a provisioning task, and repeat the read.
2. **Signed traffic.** Send a signed request and receive a signed webhook between two agents that publish `identity.brand_json_url`. Confirm agent resolution by canonical URL, and that a pinned key missing from the agent's JWKS is rejected. Against a seller that lists an operation in `required_for` and `a2a_invocation_skill` in `request_signing.operation_sources`, confirm an unsigned A2A call to that operation is rejected. A 3.3 seller that lists the operation in `required_for` without the marker must reject it too; the marker advertises enforcement, it does not enable it.
3. **Catalog intake.** For a seller that declares `media_buy.features.catalog_ingestion`, confirm `sync_catalogs` rejects an unlisted catalog type, mode, or feed format, and an explicit `content_id_type` outside a declared `supported_content_id_types`, with `UNSUPPORTED_FEATURE` before mutation, including on a dry run, and reports one `item_issues` entry per item on terminal results and discovery reads under `per_item` reporting.
4. **Delivery webhooks.** Register a `reporting_webhook` with an `operation_id` and confirm every `media_buy_delivery` webhook echoes it verbatim. Register one without it and confirm the seller sends no delivery webhooks to it.
5. **End to end.** Run one buyer and seller lifecycle through purchase, creative assignment, and a delivery readback.

## What may still change

The [3.3.0 milestone](https://github.com/adcontextprotocol/adcp/milestone/10) is the live scope record for work that may still land during the beta cycle. Use these maintained GitHub views as the live record:

- [Open 3.3 issues](https://github.com/adcontextprotocol/adcp/issues?q=is%3Aopen+is%3Aissue+milestone%3A3.3.0)
- [Open 3.3 pull requests](https://github.com/adcontextprotocol/adcp/pulls?q=is%3Aopen+milestone%3A3.3.0)
- [Closed 3.3 milestone work](https://github.com/adcontextprotocol/adcp/milestone/10?closed=1)

Milestone assignment means **candidate for the 3.3 line**, not a commitment to any particular beta or GA. A change is included in a beta only when it is merged before that beta's tag. Items may be deferred, split, or moved to a later release as working groups resolve scope and interoperability risk.

## Known beta boundaries

- Experimental surfaces retain their [experimental-status contract](/docs/reference/experimental-status). A 3.3 beta does not graduate them to stable. The surfaces new in 3.3 are listed in the [release notes](/docs/reference/release-notes#experimental-surfaces-in-3-3).
- The `3.3-beta` documentation selector moves forward; pinned semver artifacts and documentation snapshots remain immutable.
- Stable schema aliases continue to resolve to stable releases during beta. Use pinned prerelease URLs when validating beta behavior.
- The `media_buy_seller/unprovisioned_account_reference` storyboard is advisory until runner capability `14.1.0`.

## Report useful feedback

Include this information in a beta issue:

- protocol artifact version and wire pin;
- SDK name and version, or `raw wire`;
- buyer, seller, creative, signals, brand, measurement, or governance role;
- transport and task name;
- schema path or JSON Pointer involved;
- expected and actual behavior;
- minimal redacted payload and validation error;
- whether the problem blocks interoperability on the beta you tested.

Never include credentials, signed URLs, bearer tokens, private keys, or live customer payloads.
