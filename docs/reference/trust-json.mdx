`trust.json` is a proposed organization-level record of which agents an organization runs, who may act for it, and whose grants it accepts. AdCP 3.3 ships its v1 JSON schemas as an **experimental, schemas-only** foothold. It exists so implementers can review the document shape and try it out before the behavior that would use it is specified.

<Warning>
**Nothing consumes `trust.json` in AdCP 3.3.** No verifier, resolver, registry, or storyboard reads it. No agent, publisher, or buyer is required to publish it, and no capability field points to it. `brand.json` behavior is unchanged: agent resolution, request signing, webhook signing, and governance still resolve through `brand.json` and `identity.brand_json_url`. Publishing a `trust.json` today has no protocol effect, and third parties, crawlers, and registries must not treat one as authority.
</Warning>

## Status

| | |
|---|---|
| Feature id | `identity.trust_json` (see [experimental status](/docs/reference/experimental-status#current-experimental-surfaces)) |
| Schemas | `trust/v1/trust.json`, `trust/v1/trust-acknowledgements.json`; both carry `x-status: experimental` |
| Capability field | None. `identity.trust_url` is not part of 3.3 |
| Name and path | May change before graduation |
| `v1` in the path | A path namespace, not a stability promise. While the schemas are experimental they may change in breaking ways |

**The document name and path may change.** The [JournalList](https://journallist.net) `trust.txt` naming outreach is still open, so both the `trust.json` name and the `/.well-known/trust.json` location are provisional. This is one reason the surface is experimental. Do not hard-code either into anything you cannot change.

Because no seller implements a task or capability from this surface, there is nothing to declare in `experimental_features`. The feature id exists so that, when behavior arrives, the same id carries the stability contract.

## What the schemas describe

The record answers one question: which agents does this organization run, with which keys, who may act for it, and whose grants does it accept. The core is protocol-neutral. Roles and scopes are namespaced tokens such as `adcp:sales`, and AdCP defines the `adcp` namespace as the first profile.

| Field | Purpose |
|---|---|
| `agents[]` | Agents the organization runs: `url`, namespaced `roles`, optional `protocols`, `jwks_uri`, `countries`, and per-protocol `profiles` |
| `grants[]` | Authority the organization delegates: `grantee` domain, optional `agents[]` narrowing, namespaced `scopes`, `countries`, `valid_from` and `valid_until`. Grants never carry keys |
| `exclusive_grants` | When true, `grants[]` is exhaustive for the scopes it names |
| `acknowledgements[]` or `acknowledgements_url` (not both) | Grants the organization accepts, by reference: `grantor`, `agent_url`, and `via`. Terms stay in the grantor's document |
| `profiles` | Record-level per-protocol data |
| `authoritative_location` | Pointer variant for hosted records, instead of the fields above |

The top level of a record is closed. Vendor data goes under `ext.{vendor}`. The `trust-acknowledgements.json` schema is the optional sub-document that `acknowledgements_url` points to, for organizations that accept many grants.

The organization a record speaks for is the host that serves it, never a value inside the document.

### Examples

A publisher that runs one sales agent. Validated against the schema:

```json
{
  "$schema": "https://adcontextprotocol.org/schemas/v3/trust/v1/trust.json",
  "last_updated": "2026-09-30T00:00:00Z",
  "agents": [
    {
      "url": "https://ads.streamhaus.example/mcp",
      "roles": ["adcp:sales"],
      "protocols": ["mcp"],
      "jwks_uri": "https://ads.streamhaus.example/.well-known/jwks.json"
    }
  ]
}
```

A brand house that delegates authority and runs no agents. A grant names a grantee and, optionally, specific agent URLs. It never carries keys:

```json
{
  "$schema": "https://adcontextprotocol.org/schemas/v3/trust/v1/trust.json",
  "last_updated": "2026-09-30T00:00:00Z",
  "exclusive_grants": true,
  "grants": [
    {
      "grantee": "pinnacle-agency.example",
      "scopes": ["adcp:media_buying", "adcp:creative_generation"],
      "countries": ["US", "CA"],
      "valid_until": "2027-06-30T00:00:00Z",
      "profiles": { "adcp": { "brands": ["nova_cola", "nova_snacks"] } }
    },
    {
      "grantee": "sentinel-governance.example",
      "scopes": ["adcp:governance"],
      "agents": [{ "url": "https://gov.sentinel-governance.example/t/7f3a9c" }]
    }
  ]
}
```

An ad network that accepts publisher grants by reference, with the bulk entries in a sub-document:

```json
{
  "$schema": "https://adcontextprotocol.org/schemas/v3/trust/v1/trust.json",
  "last_updated": "2026-09-30T00:00:00Z",
  "agents": [
    {
      "url": "https://northwind.example/mcp/streamhaus",
      "roles": ["adcp:sales"],
      "jwks_uri": "https://keys.northwind.example/jwks/streamhaus.json"
    }
  ],
  "acknowledgements_url": "https://northwind.example/.well-known/trust-acknowledgements.json"
}
```

```json
{
  "$schema": "https://adcontextprotocol.org/schemas/v3/trust/v1/trust-acknowledgements.json",
  "last_updated": "2026-09-30T00:00:00Z",
  "acknowledgements": [
    {
      "grantor": "streamhaus.example",
      "agent_url": "https://northwind.example/mcp/streamhaus",
      "via": "adcp:adagents",
      "profiles": { "adcp": { "delegation_type": "delegated" } }
    }
  ]
}
```

## What is not in 3.3

These are planned for a later release and are deliberately absent. The MUST and SHOULD wording in the schema descriptions records the intended design for them and is not enforced by anything today.

- The `identity.trust_url` capability field.
- Resolver changes, the agent-to-trust-record binding, precedence over `brand.json`, and no-downgrade rules.
- Storyboard dual-source modes and the seller-setup rewrite.
- Any requirement to publish `/.well-known/trust.json`.
- Deprecating or removing any `brand.json` field.
