Add experimental account requests under the new feature id `account.requests` (#8280, P10 of #8118). A buyer agent calls `request_account` to ask a seller for an advertiser account; the seller matches an existing account or creates one, possibly after human review on either side. The request is its own object (`core/account-request-record.json`) with four states: `in_review` (with a `pending_action` saying whether it is waiting on the seller or the buyer, what kind of action is needed, and where), `resolved` (`account_id`, `resolution: matched | created`), `ambiguous` (`candidates[]` the caller is already granted), and `rejected`. No account exists until the request resolves, so a match never changes an `account_id`. Retries are safe through `idempotency_key`; deduplicating separate requests for the same advertiser is non-normative guidance (per calling agent, matching on brand and operator, with countries, currency, timezone, sandbox and `operator_unit` as filters). `get_account_requests` reads requests back, and the caller-anchored `account_request.changed` webhook announces seller-driven transitions. Sellers declare support in `account.requests` on `get_adcp_capabilities`.

New shared schemas: `core/pending-action.json` and the extensible `enums/pending-action-kind.json` (`review`, `sign_up`, `accept_terms`, `credit_application`, `add_payment`, `grant`, `connect_credentials`), `enums/pending-action-party.json` (`seller`, `buyer`), `core/account-candidate.json`, `enums/account-request-state.json`, `enums/account-request-resolution.json`, and `error-details/account-ambiguous.json`.

`sync_accounts` provisioning rows become a projection of the same request. Results gain optional `request_id` and `resolution`, and `setup` (on results and on `Account`) gains optional `waiting_on` and `kind`. A matched result reports `action: unchanged` with `resolution: matched`, and a declined request reports `status: rejected` with the reason in `warnings`, as today; no enum values are added. `request_id` appears only on `pending_approval` rows without an `account_id`, and `resolution` only with an `account_id`. `ACCOUNT_AMBIGUOUS` may carry `details.candidates[]`.

A seller never issues an `account_id` it might later change. While a row is `pending_approval` and may resolve to a different account, it carries `request_id` and no `account_id`; a seller whose placeholder ID is the one the account keeps MAY issue it early. This replaces the narrower `account.stable_account_id` placeholder rule. With that flag deprecated, the rule applies to every seller. A request-mode seller reports pending transitions through `account_request.changed`; on resolution it activates the row's account-level subscribers and then fires `account.status_changed` with the resolved `account_id`, so buyers that predate account requests still learn the outcome. `account.requests.event_type` is optional, and declaring it requires caller-scoped notification support. Requests never act as an existence oracle: answers for accounts outside the caller's grants are indistinguishable from no match, and action URLs are not bearer links.

The caller relationship on `get_principal` (`core/principal-relationship.json`) gains the same optional `setup.waiting_on` and `setup.kind`. `list_accounts` guidance for seller-owned namespaces: sellers SHOULD return `account_scope` on every account, with `brand` and/or `operator` where the scope names them. There is no preference order between scopes, because the choice decides who is invoiced and a person makes it.
