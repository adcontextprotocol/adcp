Make `request_account` the single account write where the seller supports `account.requests`, with `sync_accounts` superseded there and stable everywhere else (#8543, Part A).

- `request_account` changes an existing account as well as opening one. With `account_id` and other fields, each field is a requested change: the brand's `countries` (with a matching `domain` and `brand_id`), `operator_unit`, `billing`, `billing_entity`, and `payment_terms`. `currency` and `timezone` may be refused, and `sandbox` never changes. A new `revision` guards the change (`CONFLICT` when stale). It is required when the change touches `billing`, `billing_entity`, or `payment_terms`, and optional otherwise. A change resolves with the new `resolution: updated`, and the request record gains an optional `account` snapshot on `resolved`. A change the seller must approve goes `in_review` with a pending action, and the account keeps its current attributes until the request resolves.
- `list_accounts` reads requests: new optional `include_requests` and `request_ids` return `account_requests[]` beside `accounts[]`. The unreleased `get_account_requests` task is removed. `account.requests.read_task` is now `list_accounts`.
- `sync_accounts` stays stable and available in 3.3. Where the seller supports `account.requests`, `request_account`, `list_accounts` and `sync_principal` supersede it, and buyers SHOULD use them there. Its formal deprecation follows `account.requests` leaving experimental status. A `sync_accounts` entry that carries only `notification_configs` and/or `reporting_delivery_configs` is a subscription write: it MUST name an account the caller already holds (otherwise `ACCOUNT_NOT_FOUND`), and the seller MUST NOT provision, run account review, or change account attributes for it.
- `request_account` change mode authorization: the seller resolves `account_id` against the caller's access before any other validation, so an unreachable account answers exactly like an unknown one. A change requires a grant that permits it with `read_only: false`, and money fields need `field_scopes` (`SCOPE_INSUFFICIENT`, `READ_ONLY_SCOPE`, `FIELD_NOT_PERMITTED`). An `in_review` change re-checks `revision` when it resolves (`CONFLICT`). A newer change request from the same caller supersedes the open one (`CONFLICT` with `details.superseded_by`), never another caller's.
- `request_account` gains `request_id`, to pick a candidate from an `ambiguous` request or name the account created after a `sign_up` action (the request resolves as `matched`). `account.requests` gains `changeable_attributes`. The `requested` echo never includes write-only fields.
- The 3.3 creative MCP role profile gains `request_account`.
