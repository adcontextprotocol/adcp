Webhook-signing mode is now selected only by the seller's `legacy_hmac_fallback` capability and its per-counterparty onboarding record, not by a field in the registering request's body. Condition (b) of `request_signature_required` ("payload carries a field that triggers signing regardless of `required_for`") and the per-request `authentication` block as a mode trigger are deprecated in 3.x and removed in 4.0. The mode no longer comes from the body; rejection with the new code still reads the body, but it never changes mode or escalates authentication. This resolves the conflict with the "policy before body parsing" rule (adcp#7563). During the transition, a seller with `legacy_hmac_fallback: false` rejects a registration carrying `authentication.credentials` with the new `webhook_hmac_not_supported` (correctable by changing the registration, not retryable as-is) (HTTP 400) instead of `request_signature_required`; the code is added to `request-signing-error-code.json` on both `enumDescriptions` and `enumMetadata`. Sellers with `legacy_hmac_fallback: true` and no onboarding record keep the 3.x behavior. The documented-exception alternative is recorded as rejected: it makes the verifier parse unauthenticated bytes to decide whether they required authentication.

A verifier now rejects a JSON-RPC batch (a JSON array body) with `request_body_malformed` (SHOULD in 3.2.x, MUST from 3.3, per the existing hardening schedule), replacing the 3.2 interim rule that let a verifier resolve every element (adcp#7565). A signed AdCP request carries exactly one JSON-RPC message.

Conformance: vector `request-signing/negative/027` (and its 3.2 mirror) now declares `applies_when: "webhook_signing.legacy_hmac_fallback == true"` and is graded only for such agents. The functional create fixtures in `media_buy_seller` (two steps), `create_media_buy_async`, `creative_generative/seller` and `sales_broadcast_tv` no longer send `push_notification_config.authentication`, so a signing seller with `legacy_hmac_fallback: false` is not forced to fail either 027 or an unrelated create step. Webhook-emission grading of the 9421 baseline is unchanged.

Composition with the 3.3 rule that `reporting_webhook` and `artifact_webhook` may omit `authentication` (adcp#8177): the same capability-only selection applies to every webhook registration. On those two registrations the new code and condition (b) apply only to a request served at 3.3 or later, because `authentication` stays required on a request served below 3.3 and so carries no preference signal there.
