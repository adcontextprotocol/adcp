Every task response schema and async status payload now composes `core/protocol-envelope.json` through its root `allOf`, as the envelope's notes already require. On MCP and REST the envelope fields (`status`, `task_id`, `context_id`, `context`, `message`, `timestamp`, `replayed`, `adcp_error`, `push_notification_config`, `governance_context`) are siblings of the body fields at the response root, but 47 of the 124 tool response and async status schemas did not compose the envelope, and 18 closed roots and `oneOf`/`anyOf` branches rejected envelope fields outright, because draft-07 `additionalProperties` does not see properties declared through `allOf`. Generated SDK types therefore could not represent a conforming response.

- `core/protocol-envelope.json` composes `core/version-envelope.json`, so `adcp_version` and `adcp_major_version` are envelope fields on every response, stamped by the server framework rather than carried as task data. Request schemas keep composing the version envelope directly; response schemas no longer do.
- The schema build declares every envelope property on each closed response root and closed branch as a `$ref` to its envelope declaration, driven by the envelope's own property list. A local declaration of an envelope field is kept only where it narrows: a branch's `status` const or enum, a `const` pin such as the fixed `message` and `adcp_error` of an unavailable `get_reporting_status` lookup, and `context` as a `$ref` to `core/context.json`. The 66 other local copies (`task_id` ×23, `message` ×21, `replayed` ×11, the `get_reporting_status` failure branches' `adcp_version`, `adcp_major_version`, `context_id`, `timestamp` and `adcp_error`, `governance_context` on `check_governance`, and `status` on `get_task_status`) are removed, so the envelope's declarations govern. The `minLength: 1` that the compact copies of `task_id` carried moves to the envelope, and the untrusted-input guidance on the async `message` copies moves to the envelope's `message`. The root `status` enums on `decline_proposals`, `request_proposals` and `refine_proposals` are removed; their branch consts discriminate.
- Response schemas no longer narrow two envelope fields. At 35 locations: the compact proposal-flow responses pinned `replayed` to `true` at 12, and 23 response nodes, open and closed, capped `message` at 2,000 characters. The envelope's declarations govern, so a response accepts `replayed: false` and a longer `message`. A `const` pin on `message`, such as the fixed text of an unavailable `get_reporting_status` lookup, is kept.
- `core/protocol-envelope.json` states that an absent `replayed` means `false` and that a response may carry `replayed: false`; `replayed: true` appears only on a replay.
- Async status payloads and the governance responses now require `status`, which the envelope already made required on every task response. Webhook `result` examples carry the task's `status`.

No body field is added, renamed or removed.
