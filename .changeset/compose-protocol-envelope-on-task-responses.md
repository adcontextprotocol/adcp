Every task response schema and async status payload now composes `core/protocol-envelope.json` through its root `allOf`, as the envelope's notes already require. On MCP and REST the envelope fields (`status`, `task_id`, `context_id`, `context`, `message`, `timestamp`, `replayed`, `adcp_error`, `push_notification_config`, `governance_context`) are siblings of the body fields at the response root, but 43 of the 118 tool response and async status schemas did not compose the envelope, and many restated envelope fields inline. The two closed failure branches of the experimental `get_reporting_status` rejected `task_id`, `push_notification_config` and `governance_context`, because draft-07 `additionalProperties` does not see properties declared through `allOf`.

- `core/protocol-envelope.json` composes `core/version-envelope.json`, so `adcp_version` and `adcp_major_version` are envelope fields on every response, stamped by the server framework rather than carried as task data. Request schemas keep composing the version envelope directly; response schemas no longer do.
- The two `get_reporting_status` failure branches are open, as response roots and status branches are (DR-0019), so every envelope field reaches them through the composition. No response root or status branch is closed. The rejection that closure provided is stated by name: a failed lookup forbids each body field of the success view, such as `account_id`, `ledger_snapshot_id` and `revisions`, so it still reveals no resource data.
- Response schemas declare body fields only. Inline copies of envelope fields (`task_id`, `message`, `replayed`, `context` with a local description, `governance_context`, `adcp_error`, the version and correlation fields) are removed from 35 response schemas; the envelope's declarations govern. A `status` `const` or `enum` that discriminates a branch, a `context` `$ref` identical to the envelope's, and a `const` that pins a fixed value (the unavailable `get_reporting_status` lookup) stay. The `request_proposals` and `refine_proposals` responses no longer copy `adcp_version` by hand. The untrusted-input handling that the submitted `message` copies stated now lives on `core/task-message.json`, and the envelope's `replayed` says that an absent `replayed` means `false`.
- The compact proposal-flow responses (`list_products`, `request_proposals`, `refine_proposals`, `decline_proposals`, `buy_products`, `accept_proposal`, `control_media_buy`) no longer pin `replayed` to `true`; the envelope's boolean (default `false`) governs, so a response accepts `replayed: false`.
- A task-level `message` has one bound of 2,000 characters, in one definition: `core/task-message.json` (`type: string`, `maxLength: 2000`, untrusted input to the receiver). The envelope, the MCP webhook payload and the response wrapper (`core/response.json`) refer to it, so the bound does not depend on the delivery path, and the 23 response nodes that capped `message` at 2,000 themselves no longer restate it. 3.2.7's envelope, webhook payload and wrapper declared no bound, while 3.2.7 already published the 2,000 bound on the compact and submitted responses that carry the longest seller text; this patch applies that one published bound everywhere. A seller whose text is longer MUST truncate it to 2,000 characters rather than fail the task. A `const` pin on `message`, such as the fixed text of an unavailable `get_reporting_status` lookup, is kept. `core/error.json`, `core/warning.json` and messages inside task bodies keep their own bounds.
- `task_id` has one definition, `core/task-id.json` (`type: string`, `minLength: 1`, annotated `x-entity: task` and `x-max-length-4.0: 128`), that every `task_id` declaration refers to: the envelope, `tasks/get` and `get_task_status` requests and responses, the task list responses and `task_ids` filters, the MCP webhook payload and the compliance controller (which keeps its own `maxLength: 128`). An empty `task_id` identifies no task, so it is rejected: the envelope's `task_id` is the handle a caller polls and a webhook references, and 3.2.7 already published `minLength: 1` on `core/compact-task-submitted.json`. A submitted response requires `task_id` through `core/task-submitted.json` (`status: submitted` and a required `task_id`), which every submitted response body and branch composes through `allOf`, so none restates the rule and generated types see the requirement. The envelope states no conditional rule of its own. `control_media_buy` and the `buy_products`/`accept_proposal` commitment keep their local `status` const, which their OpenAPI `discriminator` needs. Likewise every working body composes `core/task-working.json` (`status: working`) and every input-required body composes `core/task-input-required.json` (`status: input-required`), so an async status payload accepts only its own status; 3.2.7 published those payloads under their status, so the pin states the existing contract. The MCP webhook payload's example that carried a `create_media_buy` result now carries a complete one.
- The `decline_proposals` completed branch accepts `status: "completed"`, as the `request_proposals` and `refine_proposals` completed branches do, instead of forbidding `status`.
- Async status payloads, the governance responses, and the `list_products`, `request_proposals`, `refine_proposals` and `decline_proposals` completed responses now require `status`, which the envelope already made required on every task response. Webhook `result` examples carry the task's `status`.

No body field is added, renamed or removed.
