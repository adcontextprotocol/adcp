Align the transport response-size defaults with the SDKs and add seller-side discovery guidance.

The MCP and A2A whole-call client defaults rise from 1 MiB to 4 MiB (4,194,304 bytes), matching what the Go, TypeScript, Python and Java SDKs and the hosted grader ship. **This loosens a limit**: a client still enforcing 1 MiB rejects a response between 1 MiB and 4 MiB that a 3.3 client accepts. A tighter default stays conformant, so there is nothing to fix in such a client, but the response it rejects is one the seller is now entitled to send. 4 MiB remains the ceiling on what any default may be, and aligning the transport defaults raises no path-specific cap: `MAX_BRAND_JSON_BYTES`, `MAX_JWKS_BYTES`, `MAX_CAPABILITIES_BYTES`, the attestation task-body and resolution-fetch caps, the `adcp_error` cap, the `format_schema` and `adagents.json` publisher-origin cap, the A2A auth-challenge cap, and the SSRF fetch caps all still govern their own paths. The 128 KiB producer interoperability target is unchanged, and the resulting 32x gap is explicitly not slack a producer may spend.

Two sub-default figures that would have become the real cap are corrected. A2A's per-DataPart check is now the call limit rather than 1 MiB: the single-artifact invariant makes the authoritative DataPart the whole response, so a tighter per-part number silently became the effective A2A cap and rejected over A2A what the byte-identical MCP call accepts. The MCP extraction algorithm's `content[].text` check is likewise the configured limit rather than a hard-coded 1 MB, because for a server that returns only `content[].text` that item is the entire response. Requirement 9 now says an aggregate budget covers nodes as well as bytes and is not the per-call default multiplied by concurrency — raising the per-call figure 4x makes the fan-out term the one that bites — and requirement 6 notes that depth and node bounds do not limit the length of a single scalar, so per-field length limits are what keep a 4 MiB string out of a log or a model context.

Adds matching seller-side guidance. Agents SHOULD keep discovery responses — `tools/list`, `get_adcp_capabilities`, and the A2A agent card — well under the default client cap, and SHOULD paginate a large catalog. Discovery is where oversize makes an agent unreachable rather than slow, and the recourse differs by surface: the agent card has no narrowing lever, `tools/list` page size is the server's choice, and `get_adcp_capabilities` can be narrowed with `protocols[]` but the signing-key discovery path does not narrow — so a capabilities document above `MAX_CAPABILITIES_BYTES` (64 KiB) fails `request_signature_capabilities_unreachable` and makes the agent's signing keys unresolvable. A reference seller implementation served a 23 MB `tools/list` and was unreachable under the cap. The new "Discovery responses stay small" section gives per-surface targets, marks the agent-card figure as editorial rather than a cap a client may enforce, notes that the capabilities figure binds agents that sign, and flags two known tensions (#8197, #8198). The 3.2 to 3.3 migration guide and the 3.3 feature narrative carry the adopter-facing versions.
