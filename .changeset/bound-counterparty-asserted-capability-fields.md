Bound the two `get_adcp_capabilities` fields whose contents a third party writes. `media_buy.portfolio.publisher_domains` and `signals.data_provider_domains` are both populated from counterparties' `/.well-known/adagents.json`, which any domain owner publishes unilaterally and without the named agent's consent. Unbounded, they let an unrelated party inflate a victim's capabilities document past `MAX_CAPABILITIES_BYTES` (64 KiB); because the signing-key discovery path fetches that document unnarrowed, the victim lost signature verification on every signed request and webhook once verifier caches rolled, not merely discovery.

**No schema constraint is added, so no previously-valid document becomes schema-invalid.** The fix is a new normative rule plus two additive optional fields. A producer MUST NOT serve a single counterparty-asserted field above 8,192 bytes, or both together above 16,384, measured as uncompressed serialized JSON so the budget composes with the consumer's decoded-byte cap. The structural bounds — at most 100 unique entries, each at most 253 characters — are declared in `x-adcp-validation` and graded by the conformance storyboard in 3.x, becoming schema constraints in 4.0; this follows the `identity.brand_json_url` `required_when` / `schema_required_when` precedent in the same schema. A count bound cannot express bytes, so the byte budget is the bound that binds: 100 realistic domains are well inside 8,192 bytes, while 100 maximum-length ones are 25,600 and are rejected by the budget rather than the schema.

The narrowing is in what counts as conformant, not in what validates: a 3.2 seller that mirrored a large network wholesale is no longer conformant. That is recorded in [3.3 exceptions to 3.x compatibility](/docs/reference/versioning#3-3-exceptions-to-3-x-compatibility-beta) alongside the other 3.3 normative narrowings.

Because bounding a list buyers read as exhaustive would otherwise make a large legitimate network look unauthorized for most of its own inventory, the rule ships with `publisher_domains_complete` and `data_provider_domains_complete` (boolean, default `true`, advisory only and never an authorization input). An agent whose list is complete changes nothing; one that truncates sets the flag `false` and MUST NOT serve a truncated list as complete. Both lists are now explicitly non-exhaustive whether or not they are marked complete: a counterparty's absence is not a denial, and each publisher's or provider's own `adagents.json` remains the authority.

The published buyer validation workflow denied on cache miss against a cache warmed only from `publisher_domains`, so it would have rejected legitimate inventory from any seller that truncates. It now resolves a publisher on demand — in one deduplicated pass, under a fixed fetch-count and concurrency cap, through the SSRF profile with the 1 MiB publisher-origin cap and no redirects, retrying rather than caching failures. `products[]` and `publisher_properties[]` are both seller-sized, so an unbounded per-property fetch would have handed the seller the buyer's fan-out.
