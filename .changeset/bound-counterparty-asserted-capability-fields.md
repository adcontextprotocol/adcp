Bound the two `get_adcp_capabilities` fields whose contents a third party writes. `media_buy.portfolio.publisher_domains` and `signals.data_provider_domains` are both populated from counterparties' `/.well-known/adagents.json`, which any domain owner publishes unilaterally and without the named agent's consent. Unbounded, they let an unrelated party inflate a victim's capabilities document past `MAX_CAPABILITIES_BYTES` (64 KiB); because the signing-key discovery path fetches that document unnarrowed, the victim lost signature verification on every signed request and webhook once verifier caches rolled, not merely discovery. **This tightens the schema**: both arrays now carry `maxItems: 100`, `uniqueItems: true`, and `maxLength: 253` per entry, so a response that was schema-valid at 3.2 with 101 domains, a duplicate, or an over-length entry is not schema-valid at 3.3. A new normative byte budget in `security.mdx` §Response Size Bounds caps any single counterparty-asserted field at 8,192 bytes as served and all of them together at 16,384 — the bound that actually binds, since a count bound cannot express bytes and a hundred maximum-length domains are thirteen times a hundred ordinary ones. The schema bound is a conformance statement, not a runtime control; the control is the agent not mirroring what asserts it.

The schema ceiling is deliberately looser than the byte budget, because a count cannot express bytes: the count binds a legitimate list (100 realistic domains are well inside 8,192 bytes), the byte budget binds an adversarial one (100 maximum-length domains are 25,600 bytes and are rejected by the budget, not by the schema). Schema-validity is therefore not conformance for these fields, and two schema-valid fields at their limits are already most of the 64 KiB document.

Because bounding a list buyers read as exhaustive would otherwise make a large legitimate network look unauthorized for most of its own inventory, the bound ships with `publisher_domains_complete` and `data_provider_domains_complete` (boolean, default `true`, advisory only and never an authorization input). An agent whose list is complete changes nothing; one that truncates sets the flag `false` and MUST NOT serve a truncated list as complete. Both lists are now explicitly non-exhaustive whether or not they are marked complete: a counterparty's absence is not a denial, and each publisher's or provider's own `adagents.json` remains the authority.

The published buyer validation workflow denied on cache miss against a cache warmed only from `publisher_domains`, so it would have rejected legitimate inventory from any seller that truncates. It now resolves a publisher on demand — in one deduplicated pass, under a fixed fetch-count and concurrency cap, through the SSRF profile with the 1 MiB publisher-origin cap and no redirects, retrying rather than caching failures. `products[]` and `publisher_properties[]` are both seller-sized, so an unbounded per-property fetch would have handed the seller the buyer's fan-out.
