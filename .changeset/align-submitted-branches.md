Align the inline `submitted` branches with their published async status files (adcp#8856). Eight tasks defined their submitted response twice, and the copies disagreed: the inline branch in `<tool>-response.json` rejected fields the published `<tool>-async-response-submitted.json` accepts, so the same response validated differently depending on which schema a validator used. The inline branches for `sync_creatives` (creatives, merges, warnings), `build_creative` (creative_manifest, creative_manifests, creatives, estimate), `control_media_buy` (media_buy_id, warnings), `create_media_buy` (media_buy_id, packages, warnings), `sync_catalogs` (catalogs, item_availability_states, item_availability_updates), and `update_media_buy` (media_buy_id, warnings) — plus the shared `media-buy-commitment-response.json` submitted branch behind `accept_proposal` and `buy_products` (media_buy_id, warnings) — no longer forbid those fields. Each fix is a recorded correction under DR-0036: the published status file already states the shape, and every value the inline branch accepted before still validates. To keep each response `oneOf` exclusive after that loosening, the success branches of `create_media_buy`, `update_media_buy` and `build_creative` also exclude a `core/task-submitted.json` body, so a submitted body carrying result fields matches the submitted branch only (the other tools' success branches already exclude it, by `task_id`/`status` or a fixed `status: "completed"`). No restructure: the bodies-only layout and generated unions stay in #8565 for 4.0.
