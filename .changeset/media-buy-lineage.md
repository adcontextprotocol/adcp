Add forward-only media-buy lineage so a renewal, migration, or sunset can name the buy it succeeds (#5849). `create_media_buy`, `buy_products`, and `accept_proposal` (when acceptance creates a new MediaBuy) take optional `predecessor_media_buy_id` (`x-entity: media_buy`) and `lineage_reason`, a new closed enum `enums/media-buy-lineage-reason.json` (`renewal`, `terms_change`, `migration`, `sunset`; anything else goes in `ext`). The two fields are supplied together or not at all. `get_media_buys` echoes both on each buy created with them (also on `core/media-buy.json`) and gains a `predecessor_media_buy_id` request filter that returns a buy's direct successors in every status (like `media_buy_ids`, it suppresses the implicit `["active"]` status default). The link is set once at creation and nothing is written back to the predecessor and its AdCP-visible state does not change, so canceled and completed buys are never mutated. It is same seller and same account only: the predecessor MUST be an existing buy the caller can access in the request's account, otherwise the seller rejects with `MEDIA_BUY_NOT_FOUND` (with `INVALID_REQUEST` for an unpaired field or a link on a `media_buy_update` or `media_buy_cancellation` acceptance, and with `UNSUPPORTED_FEATURE` when the seller cannot record the link, so it never creates an unlinked buy silently). Because the link names an already-existing buy and is never edited, a cycle cannot form, so there is no depth limit and no new error code (existing codes only). Stable, not experimental. Additive and non-breaking: requests and responses without the fields are unchanged. New normative section "Media Buy Lineage" in the media-buy specification. Decision record: DR-XXXX.
