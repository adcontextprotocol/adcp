Compliance (experimental, `media_buy.reporting_subscriptions`): the `reporting_subscription_probe` can now be reset, `set_account_timezone` has a defined response, and `owed_periods_match` tolerates history a seller purged beyond its retention.

- **Probe reset.** `reset_state` is now specified in `comply-test-controller-request.json` and the controller docs. It takes no params, returns `{ "success": true }` (`SeedSuccess`), and acts only on the caller's own sandbox. A runner that finds it in `list_scenarios` calls it once before each storyboard. A seller that lists `reporting_subscription_probe` MUST also list `reset_state`. The reset MUST unpin the caller's sandbox clock, so `simulated_now` reads the seller's wall clock again until the next `advance_time` (it does not go back to an earlier pinned instant). It MUST also discard the grant changes and timezone changes the probe made, with the coverage history they recorded. The seller either discards the sandbox accounts the probe changed or keeps them with the changes undone. Until now the spec defined no reset, so a storyboard that pinned the clock in 2031 stopped the next one from starting in 2030. The reporting-subscription storyboards check that `reset_state` is advertised.
- **`set_account_timezone` response.** `comply-test-controller-response.json` defines `SetAccountTimezoneResult`: `simulated_now`, `account_id`, `previous_timezone`, `timezone`, `changed_at` (the sandbox instant the change applied, which is absent when nothing changed), and `timezone_cutovers[]`. Each cutover entry has the shape of a `get_reporting_status` `subscription_coverage[].timezone_cutovers[]` entry and always includes `offering_id` and `previous_timezone`. `SimulationSuccess` applies this shape when `simulated.previous_timezone` is present. The coverage storyboard now checks it, and the training agent returns exactly this shape and restores probe-changed account timezones on `reset_state`.
- **`owed_periods_match` comparison window.** The window starts at the later of the expected start (the request's `period.start`, or no lower bound) and the response's `scope.ledger_retained_from`. That retention bound can be no later than `ledger_as_of` minus `status_retention_days`. Periods that start before the window are not required, and an obligation the seller returns for one is ignored rather than counted as a mismatch. Inside the window, extra or missing obligations still fail. The check stays advisory with `expires_after_version: "17.0.0"`, because no released runner implements it yet.

SDK storyboard runners implementing `owed_periods_match` must: (1) compute the retention bound as the earlier of `scope.ledger_retained_from` and `ledger_as_of − status_retention_days × 86,400 s`; (2) start the window at the later of that bound and the request's `period.start`; (3) drop periods that start before the window start from both the owed set and the seller's obligations before comparing; and (4) report the window start and which bound set it on failure. Runners should keep calling `reset_state` before each storyboard when the seller lists it, as `@adcp/sdk` already does.
