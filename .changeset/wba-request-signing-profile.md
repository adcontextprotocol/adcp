Add the Web Bot Auth request-signing profile proposed for 3.3 in RFC #7878, published alongside the AdCP RFC 9421 profile, which stays as written. The page `docs/building/by-layer/L1/wba-profile.mdx` defines the profile: a signer names its origin in a covered `Signature-Agent` header, and the verifier resolves the signer's keys in one step from that origin's `/.well-known/http-message-signatures-directory`. An identity is an origin with one key directory, every signing key is an Ed25519 key, `keyid` is the JWK thumbprint, and every signed request carries an RFC 9421 `nonce` of 64 bytes, as unpadded base64url or canonical padded base64, that the seller's verifier MUST check. Signature failures are reported with `400`, `403`, and `429`. A request carries exactly one `web-bot-auth` signature and one `Signature-Agent` member, and a verifier does not read signatures with other tags; a party that signs a request is its signer, and whether it may act for another party is answered by that party's `brand.json` or `trust.json`. A directory response is served with the `application/http-message-signatures-directory+json` media type and signed by each Ed25519 key it holds; a verifier uses each Ed25519 key with a valid signature, ignores every other key, and refuses a directory in which any key carries a private member. Webhooks under the profile are ordinary signed requests from the seller's identity. A governance agent is an identity like any other, on its own origin; JWS artifacts, such as governance tokens, are outside this profile. The profile selects options Web Bot Auth and RFC 9421 already define and adds nothing to the wire.

Two checks have no Web Bot Auth library behind them, so they live in the AdCP layer, in the `security.mdx` section "AdCP checks after Web Bot Auth verification": the identity's revocation list, signed by a key in the identity's directory with JWS `alg` `EdDSA`, and the `Accept-Signature` hint on a `403` or `429`, which is a SHOULD.

A verified identity the seller has not approved gets no account access, reads included. After approval, the identity maps to a principal and the principal to its accounts, so onboarding becomes approving a verified identity instead of issuing a credential.

Additive schema changes: `request_signing.profiles` and `webhook_signing.profiles` on `get_adcp_capabilities` let a seller say which signing profiles it accepts and emits, and an optional `signing_profile` on `push-notification-config`, `notification-config`, and `agent-notification-config` lets a webhook subscriber select the profile it verifies. Omitting every new field keeps the 3.0 to 3.2 behavior.

Adds the `wba-profile` conformance vectors: two positive vectors (single signer, signed directory response) and six negative vectors (missing nonce, replayed nonce, uncovered `Signature-Agent`, key absent from the named directory, unparseable header, two signatures on one request), each stating its expected status code. Adds `scenarios.json`, 49 failure scenarios as data that a harness signs at run time, each with its expected outcome and a tier that says whether a Web Bot Auth library alone gives that outcome or only the profile's rules do.
