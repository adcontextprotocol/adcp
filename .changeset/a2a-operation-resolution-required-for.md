Security errata for GHSA-2pm6-6mc8-8xcm (adcp#7820): `request_signing.required_for` / `supported_for` / `warn_for` match the AdCP operation resolved from the request on every transport, so they apply over A2A. This resolves a contradiction, not a new requirement: the A2A profile extension already requires the signing rules used for the equivalent task over MCP, while `security.mdx` said a `required_for` match could not be satisfied by any JSON-RPC `method` other than `tools/call`, which made `required_for` unenforceable for A2A messages and let an unsigned A2A `create_media_buy` through a seller that listed it. MCP `tools/call` resolves to `params.name`; A2A `SendMessage`, `SendStreamingMessage`, `message/send`, and `message/stream` resolve to the `skill` of the Message's sole DataPart; `protocol_methods_*` keep matching the JSON-RPC `method` only.

A request that does not resolve to exactly one operation (no or several DataParts, a FilePart, a malformed Part, duplicate keys, a non-object body) fails closed with the existing `request_body_malformed` code, and the resolved operation is the only input to the signature gate, handler dispatch, and schema selection. Adds the A2A conformance vectors under `test-vectors/request-signing/a2a/` with a generator and independent test, widens the `request_body_malformed` description, and aligns the A2A profile and account docs. Sellers that list an operation in `required_for` and serve A2A will begin rejecting unsigned A2A calls for it once their verifier adopts the corrected rule; stage through `warn_for` first.
