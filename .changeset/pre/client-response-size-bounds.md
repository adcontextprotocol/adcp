Add a client-side response-size bound to the security considerations. An agent response is untrusted input: a reply of a few tens of megabytes drives a buyer process to multi-gigabyte peak usage once decompressed and parsed, and the process dies before any other control on the page can run. Clients SHOULD bound every AdCP response they read on their own call path — MCP `tools/call`, `tools/list`, `initialize`, and transport-native `tasks/get` / `tasks/result`; A2A message and task operations including streamed frames; the A2A agent card; and `get_adcp_capabilities`. A conforming bound is enforced while the body is received rather than after buffering or parsing, pre-rejects an over-limit or self-contradictory `Content-Length`, is paired with connect, read-idle, and total deadlines, counts raw and decoded bytes with a bounded decoder output buffer, covers SSE per event and cumulatively per retained task across reconnects, bounds JSON depth (64) and node count (100,000) after the byte cap passes, errors with a distinct client-local error type instead of truncating, defaults to no more than 4 MiB (4,194,304 bytes) with per-agent and per-call override, and bounds aggregate concurrent exposure. The byte cap bounds ingress; the parse bounds bound memory. A new precedence paragraph states that path-specific caps (`MAX_BRAND_JSON_BYTES`, `MAX_JWKS_BYTES`, `MAX_CAPABILITIES_BYTES`, the attestation task-body cap, the 4096-byte `adcp_error` cap, the SSRF fetch caps) govern their own paths and that 4 MiB is a ceiling on a default, not a target.

The MCP and A2A response-extraction profiles restate the obligation on their own call paths. Both keep a 1 MiB default; A2A's whole-call default is now stated explicitly so the two transports do not diverge. Streamable HTTP may answer with a single JSON body or an SSE stream and the bound covers both, so a peer cannot escape it by choosing `text/event-stream` or by splitting a result across frames or a resumption. The pagination guidance now says sellers with large catalogs paginate rather than rely on buyers raising their limits, and notes that an unpaginated `tools/list` carrying projected schemas clears 1 MiB on its own. Also fixes a dangling `#plan-state-binding` anchor in `security.mdx`.

**This tightens a limit for adopters with very large catalogs.** A buyer SDK that adopts the default fails a response above its configured limit instead of buffering it, and the failure arrives as a mid-body connection abort rather than an `adcp_error`. Sellers whose responses exceed the limit should paginate; buyers that need a larger response from a specific known counterparty raise the limit for that agent or that call, never globally and never by disabling it. See the 3.2 to 3.3 migration guide.
