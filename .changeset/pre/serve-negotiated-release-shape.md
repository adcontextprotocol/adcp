Require responses to conform to the served release (#7718, WG-approved 2026-10-12, DR-0024). Let R be the release a response echoes in `adcp_version`. The response MUST validate against R's published schema, except that enum values added after R are exempt. The seller omits what R's schema rejects and projects shapes R defines differently, such as `oneOf`/`anyOf` arms added after R, widened types, and alternative required fields. A webhook payload follows the release served on the request that registered the webhook. A seller that cannot meet the rule for a release MUST NOT list it in `supported_versions`. The rule binds a seller that lists 3.3 or a later release, for every release it lists, and it covers `get_adcp_capabilities`. The negotiation fields (`adcp.supported_versions`, `adcp.major_versions`, the `adcp_version` echo) keep the same shape across every release of a major. `x-added-in` is defined as informative.

The rule is stated once, in `versioning.mdx` §Serving an older pin. The per-feature version gates for `impressions` and spot rows now point to it, and the migration guides link to it. The 3.3 exceptions table and the release notes record it. The 3.1 to 3.2 migration guide lists the six known divergences. The `version_negotiation` storyboard gains an optional scenario. Its checks for the echo and the `geo_regions` and `language` capability shapes are `permanent_advisory` until runners can validate against the served release's schema bundle. Signing-profile selection by negotiated version is out of scope.
