Add four URL-canonicalization conformance vectors covering step 5 when the path is empty and no query is present. No normative change: step 5 already reads "If the path is empty AND an authority is present, substitute `/`", and `docs/reference/url-canonicalization.mdx` is untouched. The vectors close a detection gap. Of the 37 cases in `test-vectors/request-signing/canonicalization.json` exactly one had an empty path, and that one carried `?x=1` — the query in step 5's illustrative example. An implementation that read the example as the condition and gated the substitution on the query therefore scored 37 of 37 while emitting `https://host` for `https://host`, where RFC 3986 §6.2.3 and step 5 both require `https://host/`. The new cases are the bare authority, a non-default port that must keep the slash after the port rather than before it, an IPv6 literal whose brackets stay inside the slash, and the empty-query spelling `https://host?` where steps 5 and 7 compose to `https://host/?`. That last one is where a query-gated reading fails on its own terms: the raw URL carries a `?` but the parsed query is the empty string. The gap is not hypothetical — the Python SDK had exactly this gating, and the four cases fail against it before its fix and pass after, with the original 37 green throughout. Canonicalization divergence is silent until it surfaces as a signature mismatch or an agent-URL authorization failure, and the same algorithm governs every URL-identifier surface in the "Where it applies" table, not only `@target-uri`.
