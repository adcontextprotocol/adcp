Add an experimental installment lifecycle and proof of publication to `by_installment[]` in `get_media_buy_delivery` (#8088; the publish notification is deferred to 3.4). New optional `installment_status` (`$ref` the existing `enums/installment-status.json`) and `publication` on `core/installment-delivery-metrics.json`. The new `core/installment-publication.json` carries `published_at`, `posts[]` (each a `core/assets/published-post-asset.json`, one per place the installment was published, so a buyer can hand a post to `sync_creatives` for paid amplification), optional `evidence` (`core/placement-evidence.json`), and optional `verified_by` (`core/brand-ref.json`; absent means seller-reported). `publication` MUST be absent on `scheduled`, `tentative`, `postponed`, `cancelled`, and `live` rows. A postponed installment keeps its `installment_ref` with a new `scheduled_at`, and a cancelled row carries no delivery metrics. A seller that declares `cancelled` MUST report a sold installment that will not run as `cancelled` rather than drop the row. `publication` is evidence, not a billing event: billing follows the accepted terms. Sellers SHOULD populate it for a digital installment reported as `published`.

Sellers declare what they report in `reporting_capabilities.available_installment_statuses`, so a missing row is not read as non-delivery. `publication` is added to `enums/available-metric.json` (and excluded from the scalar `delivery-metric-aggregate.json` ids, like `print_metrics`), so a committed proof-of-post gap shows in `missing_metrics`. `comply_test_controller` `simulate_delivery` gains `installment_delivery`, complete `installment-delivery-metrics` rows that sandbox sellers build `by_installment` from. The cluster is `media_buy.installment_lifecycle` in the experimental registry, with Availnet (a creator marketplace) as the single adopter so far.

Compatibility: rows with no `installment_status` are delivery rows as in 3.2, so existing documents stay valid. Sellers MUST NOT send `scheduled`, `tentative`, `postponed`, or `cancelled` rows to callers pinned below AdCP 3.3 (no declared pin counts as below 3.3), because 3.2 validators require `impressions` on every installment row, and MUST NOT send `available_installment_statuses` to those callers either. A `published` row that omits `impressions` follows the general version gate for optional `impressions` on delivery rows.
