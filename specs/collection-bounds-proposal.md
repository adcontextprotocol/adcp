# Bounding list sizes and string lengths (3.3 slice and 4.0 proposal)

**Status**: Draft for the working group. Follows WG Session C (2026-10-26), which decided to bound list sizes and string lengths across the protocol.

**Scope of this document**: an inventory of every unbounded array and string in `static/schemas/source/**`, a proposed limit for each, the 3.3 slice that bounds the fields allowed to change in a minor release, and the 4.0 plan for the rest. It is an internal proposal. The numbers are proposals until the owning working groups confirm them.

**Machine-readable companions** (all generated by `scripts/audit-schema-bounds.cjs`):

| File | What it holds |
|---|---|
| `scripts/schema-bounds-inventory.json` | The inventory of the tree as committed: one record per unbounded array or string, plus every inline property or collection list. |
| `scripts/schema-bounds-3-3-slice.json` | The bounds the 3.3 slice added, with the limit and tier for each. Written by `--apply`. |

## The rule that shapes everything

A minor release only adds. The additive-minor check ([#8502](https://github.com/adcontextprotocol/adcp/pull/8502), `scripts/lint-additive-minor.cjs`) compares the schemas with the last stable release (the highest 3.2.x, 3.2.8 today) and fails on a tightened bound, among other things. It exempts schemas marked `x-status: "experimental"`, and a field that did not exist in 3.2.8 has nothing to be compared with. The audit script picks the same release. So:

- A bound on a **stable** field that 3.2.8 already carries is a 4.0 change. This document proposes it and the v4 compatibility registry records it. No stable schema is edited.
- A bound on a field that is **new in 3.3** (never in a stable release) or **experimental** is allowed now. That is the 3.3 slice.

## Inventory

Counts are for main as of 2026-11-07, before the 3.3 slice. The WG discussed about 1,734 arrays in 460 files on 2026-10-26. Main has moved since: #8505 bounded most of the capabilities-related new and experimental fields, other PRs restructured or removed some, and new experimental fields arrived.

Strings skipped as already constrained: `enum` (985), `const` (608), `format: date-time` (525), `format: date` (32), `format: email` (11), `format: uuid` (18), a bounded `pattern` (526), and a string that already has `maxLength` (457). A `pattern` is bounded when it is anchored at both ends and has no `*`, `+` or `{n,}`.

`format: uri` is skipped as the task rules say, but a URI has no length limit of its own. 308 such strings exist and 304 have no `maxLength`. They are listed in the inventory under `unbounded_uri_strings`. Recommendation: treat them like other URL-shaped values and bound them at 2,048 in 4.0.

How the columns are decided:

- **Side.** The script walks every `*-request.json` and every `*-response.json`, `*-async-response-*.json` and `*-webhook*.json` schema and follows `$ref`s. A node reached only from requests is *request*, only from responses (and webhooks, which are agent-to-agent pushes) is *response*, from both is *both*. A node reached from neither is *other*: documents such as `adagents.json`, `brand.json`, registry feeds, `compliance/` and `extensions/`. *Both* is mostly shared core types (`core/product.json`, assets, targeting).
- **Stability.** *Experimental*: the node or an ancestor in its file carries `x-status: "experimental"`. *New in 3.3*: not experimental, the node or an ancestor carries `x-added-in: "3.3.0"`, and 3.2.8 does not carry the same field on the wire. *Stable*: everything else.
- **"On the wire" is checked, not assumed.** Comparing a node with the same pointer in the same released file is not enough: 3.3 moved the relying-party object from `brand.json` into a new shared file. The new file is marked `x-added-in: "3.3.0"`, yet `relying_party_id` and `scheme` shipped in 3.2.7. The script therefore walks back from each candidate to every schema that references it, and asks whether 3.2.8 has the same path from the same root, following `$ref`s on both sides. Branch indexes are ignored, so an unclear match counts as released. The first run of the script without this check proposed two bounds that the additive-minor check rejected, which is how the case was found.
- **Markers that disagree with 3.2.8** (12 nodes) are treated as stable and left alone. They are either a stale `x-added-in` or a false match from the index-blind comparison. Follow-up for the owners:
  `core/product.json` and `core/canonical-product.json` `execution_requirements`; `core/wholesale-feed-event.json` `changed_fields` (array and items) and `summary`; `creative/sync-creatives-request.json` `assignment_operations` branch 3 `creative_id` and `package_id`; `media-buy/build-creative-response.json` both `errors` arrays; `core/identity-relying-party.json` `scheme` and `relying_party_id` (moved, shipped in 3.2.7); `protocol/get-adcp-capabilities-response.json` `supported_sections`.

## Proposed limits

Every record carries a tier, a limit and a one-line rationale. The tiers follow the numbers the schemas already use. Among bounded arrays, 100 is the ceiling on lists a caller sends (`creative_ids`, `media_buy_ids`, `task_ids`, `accounts`, `changes`), and 10,000 is the ceiling on `records` and `events`. Among bounded strings, 255 is the default for ids and names (262 fields), 2,000 for prose (41), 2,048 for URLs, and 4,096 for cursors and tokens.

| Tier | Limit | Applies to | Stable fields (4.0) |
|---|---:|---|---:|
| `array-enum` | max(32, enum size) | A set of enum values. The enum bounds it. | 336 |
| `array-small` | 32 | Attributes of one object: keys, identifiers, applied filters, closed vocabularies. | 177 |
| `array-typical` | 100 | Lists nested in an object; the default when no name signal exists. | 652 |
| `array-batch` | 100 request, 1,000 response | Request batches and id lists, and the response that echoes or pages them. | 165 |
| `array-large` | 1,000 | Id, domain and handle lists on a response that scale with an account or portfolio. | 60 |
| `array-catalog` | 10,000 | Records, events, rows, inline catalog items. | 4 |
| `string-code` | 64 (30 for phone) | Codes, versions, currencies, locales, postal codes. | 206 |
| `string-id` | 255 (200 street, 100 city) | Identifiers, names, labels. | 865 |
| `string-domain` | 253 | DNS names. RFC 1035. | 65 |
| `string-text` | 2,000 | Reasons, messages, descriptions. | 200 |
| `string-url` | 2,048 | URL-shaped values. | 11 |
| `string-token` | 4,096 | Cursors, tokens, signatures, consent strings. | 43 |
| `string-body` | 100,000 | Long bodies: asset `content`, `brief`, `preview_html`, video `prompt`. | 15 |
| `string-generic` | 500 | No name signal, including `scope`, `status`, `kind` and similar names that are often free text. Needs the owning group to confirm. | 431 |
| inline property list | none | See the next section. | 48 |

The large limits and why:

- **`array-catalog` 10,000.** `core/catalog.json` `items`, `registry-feed-response` `events`, `get-media-buy-delivery-response` `reporting_rows`, `get-property-list-response` `identifiers`. These are the only fields that legitimately carry catalog-scale data in one payload. 10,000 is the ceiling already used for `records` and `events`, and 10,000 small objects fit inside the 4 MiB response default (`security.mdx`). A catalog larger than that has `url` (and pagination), which is where it belongs. Treat 10,000 as the ceiling to argue about, not a target.
- **`trust/v1/trust-acknowledgements.json` `acknowledgements` 10,000** (experimental, in the slice). It is the out-of-band shard for organizations that accept thousands of grants, so it must hold more than the 500 `trust.json` allows inline; a review caught the generic 100 inverting that design.
- **`array-large` 1,000.** Id lists a response may enumerate for an account: `media_buy_ids`, `package_ids`, `signal_refs`, `format_ids`, `placement_ids`, `collection_ids`. A seller with a large account has hundreds. On the request side the same lists get 100, to match the siblings already bounded at 100.
- **`string-body` 100,000.** The existing `content` (100,000) and `transcript` (200,000) bounds, applied to asset bodies (CSS, JavaScript, HTML, markdown, VAST, DAAST), briefs and preview markup. Anything bigger is an asset and belongs behind a URL; the 1 MiB `markup` ceiling already in the schemas covers the one place where inline markup must be larger.
- **`string-token` 4,096.** Matches the 4,096 already on `cursor`, `token` and `governance_context`. An IAB TCF consent string can reach a few KB, so it must not be bounded lower.

Rules of thumb behind the small ones: a list of more than 32 enum values, tags, keys or identifiers on one object is a modelling error; a list of more than 100 items inside a request body should be a paged read or a reference.

**Names are weak evidence.** (Two cases came out of CI.) The first version of the script gave `scope` a 64-character limit as a short code, and `governance_context` (a signed JWS) 255 as an identifier; every request that carries `governance_context` already bounds it at 4,096. `brand/rights-terms` `exclusivity.scope` is free text, and the brand and governance storyboards failed in CI with "must NOT have more than 64 characters" and "more than 255 characters". Short-code limits now apply only to names that are codes (`code`, `currency`, `country`, `region`, `language`, `locale`, `timezone`, `unit`, `version`, `namespace`, `tag`, `postal_code`). A training-agent storyboard run is the real test of a proposed limit, and the 4.0 work should run one before it ships a bound.

**Low-confidence limits.** 431 stable strings fall in `string-generic` (500) and most arrays in `array-typical` (100) were not matched by name. They are placeholders for the owning working group. Tightening is the risk, not loosening: a bound can later be raised in a minor release, and cannot be lowered.

## Property and collection lists are always out of band

The WG rule: a property or collection list is always passed by reference (`agent_url` + `list_id`, the shape of `property-list-ref.json` and `collection-list-ref.json`), never inline. The script flags every array that carries one inline, bounded or not, and gives it **no limit**. The 4.0 action is **move out of band**. 56 arrays, of which 55 are unbounded; 34 are property lists and 22 are collection lists.

By where the list sits:

**Request and response fields: these are the cases to move.**

| Field | Stability | Side |
|---|---|---|
| `core/product.json` `publisher_properties`, `collections` (and `core/canonical-product.json`) | stable | both / response |
| `core/placement-definition.json` `property_ids`, `property_tags` | stable | other |
| `core/collection-distribution.json` `property_ids` | stable | both |
| `core/publisher-property-selector.json` `publisher_domains`, `property_ids`, `property_tags` | stable | both |
| `core/collection-selection.json` `collections` | stable | both |
| `media-buy/get-products-response.json`, `list-products-response.json`, `refine-proposals-response.json`, `request-proposals-response.json`, `list-collections-response.json`, `brand/get-brand-identity-response.json` `collections` | experimental | response |
| `media-buy/list-collections-request.json` `collections` | experimental | request (already `maxItems: 100`) |
| `trusted-match/provider-registration.json` `properties` (property RIDs a provider serves) | experimental | other |
| `protocol/get-adcp-capabilities-response.json` `media_buy.portfolio.publisher_domains`, `signals.data_provider_domains` | stable | response (owned by #8198; carries `x-max-items-4.0` / `x-max-length-4.0` from #8505) |

**List authoring: sources that build a managed list.**

| Field | Stability |
|---|---|
| `property/create-property-list-request.json`, `update-property-list-request.json` `base_properties` | stable |
| `property/base-property-source.json` `property_ids`, `identifiers`, and the tag selectors | stable |
| `property/property-list-filters.json` `exclude_identifiers` | stable |
| `property/property-list.json` `base_properties` (the stored definition, returned on reads) | stable |
| `collection/create-collection-list-request.json`, `update-collection-list-request.json` `base_collections` | stable |
| `collection/base-collection-source.json` `identifiers`, `collection-list-filters.json` `exclude_distribution_ids`, `collection-list.json` `base_collections` | stable |

**Documents** (`adagents.json`, `brand.json`, `aao/agent-publishers.json`, `core/registry-event.json`): 23 arrays. Here the inline list is the publisher's declaration and is the source of truth, not a list passed between agents, so "by reference" does not apply in the same way. They are flagged and left for the WG to rule on, because 4.0 can still bound them (documents have their own byte caps, for example 2 MiB for `brand.json`).

Judgment calls:

- **Authoring needs a way in.** `create_property_list` has to receive the list from somewhere. The `publisher_domain` + `tags` and `property_ids` selectors are queries over adagents.json, but `identifiers` is a plain enumeration. Moving authoring out of band needs a fetch-by-URL or a selector-only form first. That is the WG's call, so the doc proposes no limit and does not pretend the rule is already met.
- **The resolved page of a list read by reference is not inline.** `get_property_list` `identifiers` and `get_collection_list` `collections` are the data plane of the reference mechanism and are bounded at 10,000 per page instead.
- **Experimental inline lists were not bounded in 3.3**, though they could be, because bounding them legitimises the inline shape the WG rule is removing. Seven are left unbounded: six `collections` responses and the TMP provider registration `properties`. The six experimental `collections` fields on responses are the cheapest to move: an experimental surface can change with six weeks' notice.
- **Not flagged:** `allowed_domains` and `allowed_external_domains` in asset requirements (an allow-list of script hosts, not a property list), `placement_refs` (placement references, not properties), `governance_domains` (a vocabulary), `task_types`.

## The 3.3 slice

646 bounds in 152 files, listed in `scripts/schema-bounds-3-3-slice.json`:

| Keyword | Experimental | New in 3.3 | Total |
|---|---:|---:|---:|
| `maxItems` | 229 | 19 | 248 |
| `maxLength` | 349 | 49 | 398 |

What it does not touch:

- no stable field (a node classified stable is never edited, including the 12 marker conflicts above);
- `protocol/get-adcp-capabilities-response.json` (owned by #8198) and every node reachable from it through `$ref`: 23 arrays are in the inventory as `deferred (#8198)`. #8505 has since bounded most of that response itself, and `tests/capabilities-structural-bounds.test.cjs` pins a worst-case figure that any new bound on a referenced type moves (an earlier draft of this slice moved it by 180 KB and failed that test);
- inline property and collection lists;
- seven 3.3 beta fields that the #8501 withdrawal PRs remove (next section), in the inventory as `withdrawn (#8501)`;
- five nodes the SDK generators cannot carry a bound on today (below): `core/targeting.json` `collection_lists` and `collection_lists_exclude`, `brand/update-rights-response.json` `generation_credentials`, `creative/list-creatives-response.json` `seller_revision`, and `core/reporting-subscription-coverage.json` `excluded[].package_ids`. They are in the inventory as `deferred (SDK generation)`;
- no `required`, `additionalProperties`, enum or property changes; each edit inserts one keyword after `type`, so no object is opened, closed or extended.

**Interaction with the #8501 withdrawals.** Four draft PRs withdraw 3.3 beta fields: #8765, #8762, #8758 and #8767 (stacked on #8758). A field they remove gets no bound here, so the two sides never edit the same line, whichever merges first. The script lists them in `WITHDRAWN`:

| Field | PR |
|---|---|
| `compliance/comply-test-controller-response.json` `forced.proposal_id` | #8765 (entry 1) |
| `core/sla-window.json` `business_calendar_id` | #8762 (entries 11 and 12) |
| `creative/sync-creatives-request.json` `assignments[].trackers` | #8758 (entry 21) |
| `media-buy/get-products-response.json` `refinement_applied[].result_product_id` | #8758 (entry 23) |
| `media-buy/get-products-response.json` `execution_readiness.version` | #8758 (moves to `list_products`) |
| `core/creative-assignment.json` `trackers` | #8767 |
| `core/measurement-terms.json` `billing_measurement.counting_mechanisms` | #8767 |

The list comes from comparing each PR's base and head trees node by node, and keeping the removed nodes that the slice would otherwise bound. The other withdrawn fields were already bounded on main, are stable or constrained (enum, `$ref`), or are inline `collections` lists. Two of those PRs move a field rather than drop it: #8758 moves `execution_readiness` onto `list_products`, and #8762 gives `core/creative-review-sla.json` its own `business_calendar_id`, `response_max` and `completion_max`. In the new place those fields arrive unbounded, so once this slice is on main the guard below asks for their bounds; `--apply` adds them. Once a withdrawal PR merges, its entries no longer match a node, and the summary lists them as exclusions to delete.

**Safety against the SDK generators.** The `validate-schema-bundle` workflow generates the TypeScript and Python SDKs from the PR's bundle, and both jobs failed on the first push. Four kinds of bound broke them. Each was reproduced locally with the same steps, the last on 2026-11-07 against `adcp-client` main and `adcp-client-python` `next`:

- A bounded array that the TypeScript generator hoists into a named type alias (`CollectionLists`): its `@maxItems` post-process looks for an inline `z.array(...)` and fails with "the generated schema did not contain a ZodArray". `collection_lists` and `collection_lists_exclude`.
- A bounded array inside items that the TypeScript generator reduces to `z.object({}).passthrough()` (an `allOf` of `if`/`then` rules): the same post-process finds no `ZodArray` and fails the same way. `reporting-subscription-coverage` `excluded[].package_ids`, which is new since the first push.
- A bound on a type that mixes string with another type (`["integer", "string"]`): the generator emits `z.union([...]).max(N)`, which is not a function. `seller_revision` (its description already says so). The script defers every mixed-type node.
- A Python post-generation fix that matches the unbounded field text (`fix_update_rights_legacy_response_defaults` matches `generation_credentials: list[GenerationCredential]`) reports "changed nothing" once the field carries `max_length`. `update-rights-response.json` `generation_credentials`.

With those five deferred, both generators run clean: TypeScript through `build:lib` and the creative-asset probe, Python through `regenerate-schemas`, `validate-generated` and `test_code_generation.py`. **This is a warning for 4.0**: tightening 1,442 arrays and 1,836 strings at once will meet more of these. The SDK generators need a pass first, or the bounds land in batches that each regenerate the SDKs.

**Safety against #8502.** The check compares with 3.2.8, exempts experimental schemas, and cannot compare a field 3.2.8 never carried. The slice was run through `scripts/lint-additive-minor.cjs --baseline-ref origin/main`: no new violation, and `scripts/lint-additive-minor-baseline.json` is unchanged. The same check also found the one mistake in an earlier draft of the script (the moved relying-party fields above), which is why the script compares wire paths.

**What a 3.3 beta reader sees.** `3.3.0-beta.0` through `3.3.0-beta.4` are published and carry the new-in-3.3 fields without bounds. Bounding them is not a break against any stable release, but a beta consumer that generated code from the beta schemas may see a tighter bound. The scope freeze was 2026-10-26, so after 3.3 GA these fields become stable and can no longer be tightened. This is the last chance. If the WG prefers not to tighten fields that a beta has published, drop the 19 `maxItems` and 49 `maxLength` marked new in 3.3 from the slice and keep the experimental ones.

**A bound on an experimental field is a patch-level change** under the experimental notice contract (`docs/reference/versioning.mdx`). The changeset is `patch`.

## The 4.0 plan for stable fields

1. The 1,442 stable arrays and 1,836 stable strings stay as they are in 3.x. Nothing in this PR edits a stable schema.
2. The v4 compatibility registry has one entry, `schema_bounds_required_in_4_0`, and the migration guide has a section with the tier table, so an implementer sees the limits coming. It is a `new_requirement` and is not observable by a 3.x run (`observed_by.none`), because a 3.x agent is validated against 3.x schemas that carry no bound.
3. At the 4.0 cut, regenerate the inventory, have each working group confirm or change the limit for its fields (the `string-generic` and `array-typical` rows first), and apply the result in one change. Until then the guard below holds the line for 3.3: it fails if an array or string new in 3.3 or experimental has no bound.
4. Property and collection lists move out of band in the same release, so the 25 stable inline arrays in request, response and list-authoring schemas leave them instead of gaining a limit. The 23 in documents wait for the WG's ruling (see above).
5. A staging mechanism already exists. #8505 marks stable fields of the capabilities response (and `core/error.json`) with `x-max-items-4.0`, `x-max-length-4.0` and `x-max-properties-4.0`: annotations with no validation effect in 3.x that 4.0 turns into the keywords. Once the owning groups confirm the limits, the inventory can be written out as those annotations on stable nodes, in one mechanical change. It is not done here: the limits are unconfirmed, and the task scoped schema edits to unreleased and experimental fields.

## Open questions for the WG

1. **Beta-published fields.** Tighten the 68 new-in-3.3 bounds now, or leave them to 4.0 with the stable fields (see above).
2. **`format: uri` strings.** 304 unbounded. Bound at 2,048 in 4.0?
3. **Request id lists at 100 versus 1,000.** 100 matches the bounded siblings (`creative_ids`, `media_buy_ids`, `task_ids`). Buyers with large accounts will hit it and should paginate or use a list reference.
4. **Documents (`other` side).** `brand.json` and the other fetched documents have byte caps. Whether they also get item caps is a separate decision from the task payloads.
5. **Property list authoring.** What replaces `base_properties` and `identifiers` as the way to create a list when inline is not allowed.
6. **Markers.** The 12 `x-added-in` markers that disagree with 3.2.8.
7. **SDK generators.** Who fixes the TypeScript and Python generators before the 4.0 bulk tightening, and whether the tightening lands in batches. See the SDK section above.

## Re-running

```bash
node scripts/audit-schema-bounds.cjs                    # summary
node scripts/audit-schema-bounds.cjs --apply            # add the open 3.3 bounds, update the slice file and the inventory
node scripts/audit-schema-bounds.cjs --write            # regenerate scripts/schema-bounds-inventory.json only
node scripts/audit-schema-bounds.cjs --check            # fail if the committed inventory is stale
node scripts/audit-schema-bounds.cjs --check-unreleased # fail if a new-in-3.3 or experimental array/string has no bound
```

**Regenerating after a conflict.** `--apply` is idempotent. It bounds every node whose action is `apply in 3.3`, keeps each slice record whose bound is still in the source, and drops the rest. To rebase this slice, or a PR that conflicts with it, take main's copy of each conflicting schema and of the two generated JSON files, then run `node scripts/audit-schema-bounds.cjs --apply`. To keep a field out of the slice, add it to an exclusion in the script with its reason, remove its bound by hand, and run `--apply` again.

**CI.** `--check-unreleased` runs in the Build Check workflow as `npm run lint:schema-bounds` (about 4 seconds). It is the ratchet: every new 3.3 or experimental array or string arrives with a bound, or with an exclusion that says why not. `--check` is not wired, because it would make every schema PR regenerate a 1.3 MB file. `tests/audit-schema-bounds.test.cjs` covers the script on fixture trees and runs in `test:contracts`.

**After 3.3 GA**, set `NEW_VERSION` in the script to the next minor, so the guard covers the fields new in that release and stops covering 3.3 fields, which are then stable.
