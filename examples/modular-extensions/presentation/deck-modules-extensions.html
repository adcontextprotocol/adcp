Every addition to core moves every implementer and every SDK

Added vocabulary lands inside stable schemas, so 27 experimental IDs sit in core, none graduated, and every implementer and software development kit (SDK) absorbs each one.

In the protocol

  • 27 experimental feature IDs. No ID has ever graduated.
  • 16 open pull requests add 17 more if merged, taking the list to 44.
  • The pull requests that added 26 of the 27 IDs edited 83 stable schemas.
  • 82 experimental markers sit inline in 35 stable schemas; 10 IDs added values to closed stable enums such as error-code and notification-type.
65releases, all seen by everyone

For implementers and SDKs

  • One version for everything: from v2.5.1 to v3.2.5 it moved 65 times, and every implementer saw all 65.
  • All three SDK generators ignore x-status, so experimental fields ship as ordinary typed fields.
  • By default, the Python SDK rejects a response with an unknown field inside a closed object, or an unknown enum value.
  • Each added piece of vocabulary needs another schema bundle, so every SDK regenerates and ships a release.

The cost isn't the experiments. It's that they have nowhere to live except stable core.

A stable kernel, standard modules with their own versions, and extensions at the edge

AdCP grows in two ways. The working group (WG) ships mechanism as standard modules, each with its own version, and the market ships vocabulary as extensions that attach where a module allows.

kernel module extension

  • Kernel. The transaction lifecycle, the envelope, and shared IDs. It grows only by addition.
  • Standard modules. WG-owned areas, each with its own version and digest: buying (in eight layers), creative, governance, reporting, accounts, signals, identity, sponsored-intelligence, and trusted-match, plus the compliance-testing leaf. 0.x means experimental.
  • Extensions. Typed packages pinned by uri@digest, which attach only at extension points and open unions that a module declares. The WG hosts some; vendors publish others.

The kernel defines the envelope once; each extension defines what goes inside

The kernel adds only what it needs to carry data it can't understand; everything else about an extension lives in the file that uri@digest names.

  • The kernel adds no fields for features. Fields that describe advertising (budget, make-goods, pricing, formats) never enter the kernel; they live in modules and extensions.
  • The kernel adds only what it needs to carry data it can't understand:
    • uri: which definition;
    • digest: which exact version, so signed terms can't change silently;
    • data: the fields, which the kernel never reads;
    • the must-understand rule: whether a receiver without the definition rejects or ignores the entry.
  • Two small parts go with them: the marker a module uses to declare an extension point, and the seller's and buyer's declaration lists (declared_extensions, understood_extensions).
  • Everything else about an extension lives in the external file that uri@digest points to.
  • 🔌 The kernel is like an electrical socket standard, not the appliances. Even where extensions attach is each module's choice; the kernel only provides the marker.

Typed access needs no change to a core SDK class

The core SDK compiles each class once and never changes. The app's generated layer subclasses the classes that an extension point reaches and adds one typed attribute per extension.

If an extension adds a field to a core object, how does an SDK module add it without changing the generic SDK? Redefine the class? Attach fields at runtime?
  • No core class changes, and the binding attaches nothing at runtime. The 5,730 files in adcp and every file of @adcp/sdk hash the same before and after you add an extension.
  • The app's generated layer composes, once per build: a subclass of each host class (CommercialTerms(_sdk.CommercialTerms)) and of its parents up to each response, one attribute per enabled extension, a wrap validator (envelope to attribute), and a wrap serializer (attribute to envelope).
  • Type checkers see the attribute. pyright and tsc accept proposal.commercial_terms.makegood_units.rules[0].max_units. Remove the extension from adcp.config.json, regenerate, and every use fails type-checking.
  • Two versions coexist. One build with makegood-units 1.5.0 and 1.3.0 gets makegood_units and makegood_units_v1_3; the digest on the wire picks one.
  • The cost: the app regenerates on every added or removed extension, every version bump, and every SDK bump, and commits the output. An app that already subclasses SDK classes chooses which chain re-points the parents.

Step 4

  • The task ID <uri>#request_makegood carries no digest, so code that names the task survives a digest change.

Eight technical decisions, each with its reason

The design rests on eight technical decisions, each with one reason; this is the only slide that names the rejected alternatives.

#DecisionReasonRejected alternative, and why it lost
13Extension data travels in the extension envelope {uri, digest, data} at extension points that modules declare.Core stays untouched, extensions can't collide on field names, and the entry names the exact schema that checks it.Inline fields (the extension's fields placed on the host object under a namespaced key): every host object must open up, the key carries no version, two versions collide silently, and a strict seller boundary drops adcp:makegood_units silently while the envelope survives (measured in the binding demo and a real sales agent).
22Identity is uri plus digest; must-understand applies inside signed terms.Signed terms can't change silently for either party, and a receiver without the exact definition rejects instead of guessing.Identity by name only: one name can mean two versions, and a receiver can't tell them apart.
31The kernel holds only the envelope, the extension-point marker, and the declaration lists.The kernel never changes for a feature; where extensions attach is each module's choice.A kernel list of extension points: every added point becomes a kernel change.
4Star topology: modules depend only on the kernel and refer to each other by kernel IDs; a combination of two modules is a bridge extension.A module ships a major without forcing a release of any other module; only the bridges that touch it follow.A chain of module dependencies: one module's major ripples down the chain.
5Buying is split into eight layers with one-way dependencies.An added pricing model lands in pricing alone, and a seller that implements supply doesn't track offer.One buying module with one version: every buying change moves every buying implementer.
6SDK: generated binding. Core classes compile once; each app generates its own typed layer from the extensions it declares, so extension fields are plain attributes.Extension data reads as proposal.commercial_terms.makegood_units, the core package is never changed or rebuilt, and an app's boundary keeps "the DTO is the accepted schema".Runtime binding (one shared SDK, a registry passed at parse time, typed accessors): every parse must carry the registry, and types reach code only through the accessor. It stays as the fallback for runtime plug-ins.
74An extension's rules live in its spec, storyboards, and reference code, all pinned by its digest.One uri@digest gives the buyer SDK, the conformance runner, and the reviewer the same rules.Schema-only extensions: JSON Schema can't carry rules such as "bounds count from the accepted value".
8Releases ship as bundles: one release number resolves to kernel, module, layer, and extension versions.A seller configures one number, the SDK resolves the rest, and certification grades bundles.Pinning every module version by hand: the version matrix grows with every module.

3.3 keeps market vocabulary out of core, 3.4 lands modules and extensions, and 4.0 makes the slated removals

The plan is short because no payload changes a byte. 3.4 ships the extension mechanism, the module versions, and every byte-preserving fix at once, and adds optional fields only; 4.0 makes only the slated removals.

3.3

  • The fixes planned for 3.3, with no schema moves and no wire change.
  • Market vocabulary in flight stays out of closed core schemas: the rate card (#7955) ships as rate-card-index and the allowance kinds (#8102) as seller-adjustable-terms, once 3.4 declares the extension points.

wire: no change

3.4: modules and extensions

  • The extension mechanism in the kernel: ExtensionEntry, the extension-point marker, branch IDs, declared_extensions, and understood_extensions.
  • Extension points and open unions declared by the modules that own them, and the task union.
  • Module and layer versions: the optional modules map.
  • The byte-preserving fixes, and zero violations enforced in CI.
